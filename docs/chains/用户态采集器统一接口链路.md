# 用户态采集器统一接口链路

## 1. 结论

“用户态采集器层，上层各采集器实现统一接口，每个负责一个维度：CPU、内存、磁盘、网络、软中断。统一接口的好处是调度层不用关心底层差异。”这段表述和当前代码一致。

更精确地说：

- 统一接口是 `MonitorInter`。
- 核心方法是 `UpdateOnce(MonitorInfo*)`，每个采集器把自己的指标填进同一个 `MonitorInfo`。
- 调度层是 `MetricCollector`。
- `MetricCollector` 用 `std::vector<std::unique_ptr<MonitorInter>>` 保存所有采集器。
- 每轮采集时，`MetricCollector::CollectAll()` 只遍历 vector 并调用 `monitor->UpdateOnce(monitor_info)`。
- 底层差异被封装在各个采集器内部：有的读 `/proc`，有的读 `/dev + mmap`，网络可以走 `/proc/net/dev` 或 eBPF。

## 2. 总体链路

```text
MonitorPusher::PushOnce
    -> 创建 MonitorInfo
    -> MetricCollector::CollectAll
    -> 遍历 vector<unique_ptr<MonitorInter>>
    -> 对每个采集器调用 UpdateOnce(MonitorInfo*)
    -> 各采集器填充自己的 protobuf 字段
    -> 返回填好的 MonitorInfo
    -> 后续 Push 给 Manager
```

这层的核心设计点是：调度层只认识 `MonitorInter`，不认识每个采集器的底层采集方式。

## 3. 统一接口 MonitorInter

统一接口定义在 [worker/include/monitor/monitor_inter.h:8](../../worker/include/monitor/monitor_inter.h#L8)：

```cpp
class MonitorInter {
 public:
  MonitorInter() {}
  virtual ~MonitorInter() {}
  virtual void UpdateOnce(monitor::proto::MonitorInfo* monitor_info) = 0;
  virtual void Stop() = 0;
};
```

这里有两个关键点：

- `UpdateOnce()` 是纯虚函数，所有具体采集器必须实现。
- 参数统一是 `MonitorInfo*`，所以所有采集器都向同一个 protobuf 聚合对象写数据。

可以把这个接口理解成：

```text
不管你采 CPU、内存、磁盘、网络还是软中断，
只要你能实现 UpdateOnce(MonitorInfo*)，
调度层就可以统一调你。
```

## 6. 采集器注册

采集器注册发生在 [metric_collector.cpp:31](../../worker/src/monitor/metric_collector.cpp#L31)：

```cpp
monitors_.push_back(std::make_unique<CpuLoadMonitor>());
monitors_.push_back(std::make_unique<CpuStatMonitor>());
monitors_.push_back(std::make_unique<CpuSoftIrqMonitor>());
monitors_.push_back(std::make_unique<MemMonitor>());
#ifdef ENABLE_EBPF
  monitors_.push_back(std::make_unique<NetEbpfMonitor>());
#else
  monitors_.push_back(std::make_unique<NetMonitor>());
#endif
monitors_.push_back(std::make_unique<DiskMonitor>());
monitors_.push_back(std::make_unique<HostInfoMonitor>());
```

这里体现了接口抽象的好处：

- CPU、内存、磁盘、网络、软中断底层采集方式完全不同。
- 但它们都能作为 `MonitorInter` 放进同一个 vector。
- 网络采集可以在 `NetMonitor` 和 `NetEbpfMonitor` 之间切换，而 `CollectAll()` 不需要改。

## 7. 统一调度 CollectAll

统一调度函数在 [metric_collector.cpp:51](../../worker/src/monitor/metric_collector.cpp#L51)：

```cpp
void MetricCollector::CollectAll(monitor::proto::MonitorInfo* monitor_info) {
  if (!monitor_info) {
    return;
  }

  monitor_info->set_name(hostname_);

  for (auto& monitor : monitors_) {
    monitor->UpdateOnce(monitor_info);
  }
}
```

这段代码没有判断“当前 monitor 是 CPU 还是内存”，也没有判断“网络是 eBPF 还是 procfs”。它只做统一循环调用。

这就是“调度层不用关心底层差异”的代码证据。

## 8. Stop 生命周期统一收口

析构时同样通过统一接口收口，位置在 [metric_collector.cpp:45](../../worker/src/monitor/metric_collector.cpp#L45)：

```cpp
MetricCollector::~MetricCollector() {
  for (auto& monitor : monitors_) {
    monitor->Stop();
  }
}
```

大多数普通采集器的 `Stop()` 是空实现；`NetEbpfMonitor` 的 `Stop()` 会清理 eBPF TC hook 和 skeleton 资源。

因此 `Stop()` 也是同一个抽象接口的一部分，用来给需要清理资源的采集器预留生命周期出口。

## 9. 为什么这个设计有价值

这个设计的价值主要有三个：

1. 调度层简单  
   `MetricCollector` 只负责遍历和调用，不需要知道每个指标怎么采。

2. 底层差异隔离  
   CPU 可以走 `/dev + mmap`，内存可以走 `/proc/meminfo`，网络可以走 eBPF，这些差异都封装在各自的 `UpdateOnce()` 里。

3. 扩展新指标成本低  
   如果后续要加一个新维度，例如 TCP 重传、连接数、文件描述符数量，只需要新增一个类继承 `MonitorInter`，实现 `UpdateOnce()`，再注册到 `MetricCollector`。

## 10. 面试表达版本

可以这样讲：

> 用户态采集器层做了一个统一抽象，所有采集器都继承 `MonitorInter`，核心接口是 `UpdateOnce(MonitorInfo*)`。CPU、内存、磁盘、网络、软中断这些采集器各自封装底层采集逻辑，比如 CPU 和软中断走 `/dev + mmap`，内存走 `/proc/meminfo`，磁盘走 `/proc/diskstats`，网络可以走 `/proc/net/dev` 或 eBPF。上层 `MetricCollector` 只维护一个 `vector<unique_ptr<MonitorInter>>`，每轮采集统一遍历并调用 `UpdateOnce`，不需要关心底层到底是 procfs、字符设备 mmap 还是 BPF map。这样调度层很稳定，新增采集维度时只需要实现同样接口并注册进去。
