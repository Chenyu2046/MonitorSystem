# 采集失败隔离与回退机制

## 1. 结论

这段表述和当前代码基本一致：

> 采集器之间是解耦的，CPU 或软中断设备打不开时会跳过当前维度，不影响内存、磁盘、负载等其他维度继续采集；CPU 负载有明确的 `/dev` 到 `/proc/loadavg` 回退。网络采集是编译期选择 eBPF 或 `/proc/net/dev`，不是运行时自动切换。Worker 推送失败不会崩，下一轮继续尝试；Manager 有后台线程定期清理 60 秒未更新的主机。

需要补充两个边界：

- CPU stat 和 softirq 的失败处理是“当前采集器直接 return”，不是统一异常捕获；当前代码没有 try/catch 包住每个采集器。
- `NetEbpfMonitor` 初始化失败时会打印 “falling back to /proc/net/dev”，但当前主链路里没有运行时创建 `NetMonitor` 接管，所以网络路径应说成“编译期选择”，不要说“运行时自动切换”。

## 3. 为什么很多函数无法跳转

你在源码里看到的很多函数不是项目自己写的，而是 Linux 内核 API、内核宏或 libbpf API，所以普通 C++ 项目索引不一定能直接跳转。

例如 `cpu_stat_collector.c` 里的这些函数/宏来自 Linux 内核头文件或内核子系统：

| 函数或宏 | 来源与作用 |
| --- | --- |
| `alloc_chrdev_region` | Linux 字符设备框架，动态分配设备号 |
| `cdev_init` | 初始化 `struct cdev` |
| `cdev_add` | 把字符设备注册进内核 |
| `class_create` | 创建设备类，配合 udev 生成 `/dev` 节点 |
| `device_create` | 创建具体设备节点 |
| `struct file_operations` | Linux VFS 字符设备操作表 |
| `remap_pfn_range` | 把物理页映射到用户态 VMA |
| `hrtimer_init` / `hrtimer_start` | Linux 高精度定时器 API |
| `kcpustat_cpu` | 读取内核 per-CPU CPU 统计 |

这些不是系统调用本身，而是内核模块开发时使用的内核内部 API。要能跳转，编辑器需要知道 Linux kernel headers 或完整内核源码路径，并且 C/C++ 索引器要按内核模块编译参数建立索引。否则看到它们“无法跳转”是正常的。

用户态的 eBPF / libbpf 相关函数也是类似：

| 函数 | 来源 |
| --- | --- |
| `bpf_tc_attach` | libbpf |
| `bpf_map_lookup_elem` | libbpf / bpf syscall wrapper |
| `net_stats_bpf__open` | bpftool 生成的 skeleton |

所以判断时可以分三类：

- 项目自己写的函数：应该能在仓库里跳转。
- Linux 内核 API：需要 kernel headers 或 kernel source 才容易跳转。
- 生成代码或第三方库 API：需要生成文件、依赖头文件和索引配置。

## 4. 采集器之间为什么解耦

调度层在 [metric_collector.cpp:60](../../worker/src/monitor/metric_collector.cpp#L60) 只做一件事：遍历所有采集器并调用统一接口。

```cpp
for (auto& monitor : monitors_) {
  monitor->UpdateOnce(monitor_info);
}
```

各采集器被注册到同一个列表中，位置在 [metric_collector.cpp:31](../../worker/src/monitor/metric_collector.cpp#L31)：

```cpp
monitors_.push_back(std::make_unique<CpuLoadMonitor>());
monitors_.push_back(std::make_unique<CpuStatMonitor>());
monitors_.push_back(std::make_unique<CpuSoftIrqMonitor>());
monitors_.push_back(std::make_unique<MemMonitor>());
#ifdef ENABLE_EBPF
  monitors_.push_back(std::make_unique<NetEbpfMonitor>());
#else
  monitors_.push_back(std::make_unique<NetMonitor>());
#endif
monitors_.push_back(std::make_unique<DiskMonitor>());
monitors_.push_back(std::make_unique<HostInfoMonitor>());
```

每个采集器内部处理自己的失败。只要它没有让进程崩溃，也没有抛出未捕获异常，后面的采集器就会继续执行。

## 5. CPU stat 设备打不开时跳过当前维度

CPU 使用率采集实现位于 [cpu_stat_monitor.cpp:11](../../worker/src/monitor/cpu_stat_monitor.cpp#L11)。

它打开 `/dev/cpu_stat_monitor`：

```cpp
int fd = open("/dev/cpu_stat_monitor", O_RDONLY);
if (fd < 0) return;
```

如果内核模块没有加载、设备节点不存在、权限不足，`open` 会失败。当前实现直接 `return`，也就是跳过 CPU stat 这一维度。

如果 `mmap` 失败，也只关闭 fd 并返回：

```cpp
if (addr == MAP_FAILED) {
    close(fd);
    return;
}
```

所以 CPU stat 失败不会阻止内存、磁盘、网络等后续采集器执行。

## 6. 软中断设备打不开时跳过当前维度

软中断采集实现位于 [cpu_softirq_monitor.cpp:21](../../worker/src/monitor/cpu_softirq_monitor.cpp#L21)。

它打开 `/dev/cpu_softirq_monitor`：

```cpp
int fd = open(DEVICE_PATH, O_RDONLY);
if (fd < 0) {
  return;
}
```

`mmap` 失败时同样只返回：

```cpp
if (addr == MAP_FAILED) {
  close(fd);
  return;
}
```

因此软中断维度失败不会拖垮其他维度。

## 7. CPU Load 有 `/dev` 到 `/proc/loadavg` 回退

CPU Load 采集实现位于 [cpu_load_monitor.cpp:23](../../worker/src/monitor/cpu_load_monitor.cpp#L23)。

它先尝试打开字符设备：

```cpp
int fd = open("/dev/cpu_load_monitor", O_RDONLY);
```

如果打开并 `mmap` 成功，就直接从映射内存读取 load 并返回。

如果 `/dev/cpu_load_monitor` 不可用，代码继续走后备逻辑：

```cpp
if (ReadLoadFromProc(&load1, &load3, &load15)) {
  ...
}
```

`ReadLoadFromProc()` 定义在 [cpu_load_monitor.cpp:14](../../worker/src/monitor/cpu_load_monitor.cpp#L14)，读取的是：

```cpp
FILE* fp = fopen("/proc/loadavg", "r");
```

所以 CPU Load 的确有明确的 `/dev` 到 `/proc/loadavg` fallback。

## 8. 网络采集是编译期选择，不是运行时自动切换

网络采集器选择发生在 [metric_collector.cpp:36](../../worker/src/monitor/metric_collector.cpp#L36)：

```cpp
#ifdef ENABLE_EBPF
  monitors_.push_back(std::make_unique<NetEbpfMonitor>());
#else
  monitors_.push_back(std::make_unique<NetMonitor>());
#endif
```

`ENABLE_EBPF` 来自构建配置。开关定义在 [worker/CMakeLists.txt:17](../../worker/CMakeLists.txt#L17)：

```cmake
option(ENABLE_EBPF "Enable eBPF-based network monitoring" ON)
```

如果依赖满足，CMake 会定义 `ENABLE_EBPF=1`，位置在 [worker/CMakeLists.txt:89](../../worker/CMakeLists.txt#L89)：

```cmake
target_compile_definitions(worker PRIVATE ENABLE_EBPF=1)
```

因此当前代码是：

- 编译期有 `ENABLE_EBPF`：注册 `NetEbpfMonitor`
- 编译期没有 `ENABLE_EBPF`：注册 `NetMonitor`

虽然 [net_ebpf_monitor.cpp:89](../../worker/src/monitor/net_ebpf_monitor.cpp#L89) 会打印 “falling back to `/proc/net/dev`”，但当前实现里 `NetEbpfMonitor` 初始化失败后只是 `loaded_ = false`，`UpdateOnce()` 会直接返回，没有运行时创建 `NetMonitor` 继续采集。因此不能把它说成运行时自动切换。

## 9. Worker 推送失败不会崩，下一轮继续

Worker 的推送循环在 [monitor_pusher.cpp:45](../../worker/src/rpc/monitor_pusher.cpp#L45)：

```cpp
while (running_) {
  if (!PushOnce()) {
    std::cerr << "Failed to push monitor data to " << manager_address_
              << std::endl;
  }

  for (int i = 0; i < interval_seconds_ && running_; ++i) {
    std::this_thread::sleep_for(std::chrono::seconds(1));
  }
}
```

每轮推送由 `PushOnce()` 执行，位置在 [monitor_pusher.cpp:59](../../worker/src/rpc/monitor_pusher.cpp#L59)。

gRPC 调用失败时只是打印错误并返回 `false`，位置在 [monitor_pusher.cpp:183](../../worker/src/rpc/monitor_pusher.cpp#L183)：

```cpp
grpc::Status status = stub_->SetMonitorInfo(&context, info, &response);
```

失败分支：

```cpp
std::cerr << ">>> Push failed: " << status.error_message() << " <<<" << std::endl;
return false;
```

外层 `PushLoop()` 收到 `false` 后不会退出进程，而是等待下一个周期继续尝试。

当前没有本地补传队列，也没有落盘缓存，所以它是“失败后下一轮继续”，不是“可靠消息补偿”。

## 10. Manager 定期清理 60 秒未更新主机

Manager 侧在线主机状态存放在 `host_scores_`，定义见 [host_manager.h:58](../../manager/include/host_manager.h#L58)：

```cpp
std::unordered_map<std::string, HostScore> host_scores_;
```

收到 worker 数据后会更新这个 map，位置在 [host_manager.cpp:225](../../manager/src/host_manager.cpp#L225)：

```cpp
host_scores_[host_name] = HostScore{info, score, now};
```

后台清理逻辑在 [host_manager.cpp:107](../../manager/src/host_manager.cpp#L107) 附近。线程每 60 秒检查一次：

```cpp
std::this_thread::sleep_for(std::chrono::seconds(60));
```

然后计算每个主机距离上次更新的秒数：

```cpp
auto age = std::chrono::duration_cast<std::chrono::seconds>(
    now - it->second.timestamp).count();
```

超过 60 秒就删除：

```cpp
if (age > 60) {
  it = host_scores_.erase(it);
}
```

所以“Manager 有后台线程定期清理 60 秒未更新的主机”成立。更准确地说，它清理的是 manager 内存中的 `host_scores_` 在线评分缓存。

## 11. 面试表达版本

可以这样讲：

> 这块我不会把它说成强可靠采集系统，而是一个维度解耦、失败隔离的周期采集系统。所有采集器都实现 `UpdateOnce(MonitorInfo*)`，调度层只是遍历调用。CPU stat 和软中断依赖 `/dev/cpu_stat_monitor`、`/dev/cpu_softirq_monitor`，设备打不开或 `mmap` 失败时当前采集器直接返回，不影响内存、磁盘、负载这些维度继续填充。CPU Load 这块有明确 fallback，优先走 `/dev/cpu_load_monitor`，失败后读 `/proc/loadavg`。网络要讲严谨：它是编译期根据 `ENABLE_EBPF` 选择 eBPF 或 `/proc/net/dev`，不是运行时自动切换。Worker 推送失败只打印错误，下一轮继续尝试；Manager 侧后台线程每 60 秒检查一次，超过 60 秒没有更新的主机会从在线评分缓存里清理掉。
