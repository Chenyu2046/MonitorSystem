### 01. 对于linux分布式性能监控这个项目，在我不熟悉这个系统的情况下，你给我介绍一下这个系统

这个项目我会定位成一个 **Linux 分布式性能监控与动态负载评估工程原型**，不是生产级监控平台。整体链路可以按数据流讲。

**第一步是 Worker 采集。** Worker 部署在被监控节点，周期性采集 CPU、Load、内存、磁盘、网络和 SoftIRQ 指标。CPU 状态和 SoftIRQ 通过自研内核模块暴露字符设备，用户态用 `mmap` 读取共享页面；网络有 TC eBPF 和 `/proc/net/dev` 两种编译期实现；内存、Load、磁盘主要走 procfs。

**第二步是 gRPC Push 上报。** Worker 把各维度指标组装成 Protobuf 的 `MonitorInfo`，通过同步一元 gRPC 主动 Push 给 Manager。当前没有本地 WAL、重试队列和补传，所以它是周期上报链路，不是可靠消息系统。

**第三步是 Manager 处理。** Manager 收到数据后维护主机最新状态，计算 CPU、内存、Load、磁盘、网络五维健康评分和相邻样本变化率，再写入 MySQL 的主表和明细表，并提供查询接口。

**第四步是异常和查询。** 当前异常检测主要是阈值和变化率规则，不是 AI 预测系统。它能用于展示整体压力、趋势和异常线索，但不能单独完成根因诊断。

当前源码已经打通采集、上报、评分、入库和查询主链路；不足也比较明确：整机 CPU 聚合、diskstats 字段解析、网络速率单位、eBPF 运行时回退、CPU/SoftIRQ fallback 和部分历史状态并发访问都还需要修。

### 02. 对于这个性能监控项目，你觉得从技术上来讲，这个系统最关键的几个点是什么

我觉得关键点有三个。

**第一是内核态到用户态的数据通路。** 项目里 CPU 和 SoftIRQ 不是每轮读文本文件，而是内核模块定时把累计统计值写到共享缓冲区，用户态通过字符设备 `mmap` 映射后读取。准确地说，`open()`、`mmap()`、`munmap()` 本身仍然是系统调用；优势是映射建立以后，后续读采样数据不需要每次走 `read()`，也少了一次内核缓冲区到用户缓冲区的数据拷贝。

**第二是 Push 模型的工程权衡。** Push 和 Pull 都能做秒级监控，本项目选 Push，是因为 Worker 本地采样后直接上报，Manager 不需要主动维护所有 Worker 的访问地址，对地址动态变化或 NAT 后的节点更简单。代价是背压、重试和补传要由 Worker 侧补，目前版本还没完整实现。

**第三是多维评分。** 系统设计上把 CPU、内存、Load、磁盘、网络做归一化加权，输出一个综合健康分，方便快速排序和选节点。但我会强调，这个分数依赖基础指标正确性；当前源码里 CPU 聚合、磁盘解析和网络单位还要先修，评分才有稳定可信的意义。

### 03. 为什么选择 Push 模式而不是 Pull 模式？

结论是：不是因为 Pull 做不了实时监控，而是这个项目的 Worker-Agent 架构用 Push 更直接。

数据流是 Worker 本地采集，组装 `MonitorInfo`，然后调用 Manager 的 `SetMonitorInfo`。这样 Manager 不需要保存每个 Worker 的可访问地址，也不用主动轮询；Worker 扩缩容、IP 变化或者部署在 NAT 后面时，接入成本更低。

代价也很清楚。Push 下 Manager 的背压控制弱一些，Worker 需要自己处理发送失败、重试、本地缓存和补传。当前版本推送失败只是打印错误，下一轮继续尝试；Manager 侧有 60 秒离线清理，但没有端到端可靠投递。所以我会把它讲成“工程原型里更简单的上报模型”，不会说 Pull 不适合实时监控。

### 04. 性能采集这块有涉及哪些模块，包括涉及哪些代码逻辑，整体偏向技术的summary的东西讲讲

可以分四层讲。

**内核模块层。** CPU 状态和 SoftIRQ 各有一个 C 语言内核模块，用高精度定时器每秒读取内核已有的累计统计值，写入共享内存，再通过字符设备 `mmap` 暴露给用户态。

**eBPF 网络层。** 网络采集在启用 eBPF 时把程序挂到网卡的 TC ingress 和 egress，包经过时按 ifindex 累加字节数和包数；用户态定时读 BPF map 做差，计算速率。它的覆盖范围只限于成功挂载的接口和方向，不是天然覆盖系统所有流量。

**用户态采集器层。** Worker 里不同采集器实现统一接口，包括 CPU、Load、内存、磁盘、网络、SoftIRQ 和主机信息。`MetricCollector` 负责逐个调用采集器，把结果填到 Protobuf。

**上报层。** `MonitorPusher` 后台线程周期调用 `CollectAll`，然后通过 gRPC Push 给 Manager。当前采集失败通常是跳过对应维度，不会让 Worker 直接崩溃，但 fallback 不完整，尤其 CPU、SoftIRQ 和 eBPF 运行时失败需要后续补。

### 05. 监控项目是团队吗，主要负责

这个项目是我独立完成的工程原型，从需求拆解、架构设计到代码实现都自己做。投入最多的是三块：内核模块加 `mmap` 的 CPU/SoftIRQ 采集，TC eBPF 网络采集，以及 Manager 侧评分、入库和查询链路。

我不会把它描述成生产系统。当前价值是把 Linux 底层采集、用户态 Agent、gRPC Push、Protobuf、MySQL 存储和评分模型串起来；工程上还缺可靠补传、安全认证、指标正确性修复和更完整的压测验证。

### 06. 性能监控项目熟悉哪个模块

最熟的是 Worker 采集到 Manager 入库这条主链路，尤其是内核采集部分。

CPU/SoftIRQ 的路径是：内核模块定时读取内核累计值，写入共享缓冲区；用户态采集器打开 `/dev/cpu_stat_monitor` 或 `/dev/cpu_softirq_monitor`，通过 `mmap` 映射后读结构体；再基于上一次采样做差，算 CPU 百分比或 SoftIRQ 每秒速率；最后填入 `MonitorInfo` 推给 Manager。

这块我也知道当前不足：它不是 ring buffer，没有版本号或 seqcount 来保证多字段快照一致；设备打不开时 CPU 和 SoftIRQ 维度会缺失，没有完整 procfs fallback。

### 07. 系统如何保证高可用？

实话说，当前版本只能算基础容错，不能叫完整高可用。

已经做的部分是：Worker 里的采集器相互独立，某个维度失败不会直接拖垮整个进程；Push 失败后 Worker 不退出，下一轮继续尝试；Manager 维护最新主机状态，并有后台线程清理长时间未更新的主机。

但没做的也要讲清楚：Manager 是单点；gRPC 用的是明文连接；Worker 没有本地 WAL、重试队列和补传；MySQL 写失败不会反馈给 Worker；eBPF 初始化失败虽然日志里说 fallback，但源码里没有真正切到 `/proc/net/dev`；CPU 和 SoftIRQ 也没有完整 fallback。所以当前只能说是“采集链路具备一定失败隔离”，不是高可用系统。

### 08. 如果说让你在这个系统上去做一些高可用方面的一些设计，你现在其实是单点的嘛，你管理server是一个，让你来做你要怎么设计

我会优先把 Manager 接收层做成无状态多实例，而不是一上来做复杂主备。

第一层是 **入口高可用**：Worker 通过服务发现或负载均衡访问多个 Manager 实例，Manager 收到样本后只做校验、落队列和返回。样本里带 `host_id + collect_timestamp + sequence_id`，后端用唯一键保证幂等，避免补传或重试导致重复写。

第二层是 **削峰和可靠性**：Manager 后面接持久化消息队列，评分和入库由消费者处理。Worker 侧加有界 WAL，Manager 不可用时先落本地，恢复后按时间顺序补传。

第三层是 **存储高可用**：MySQL 不能还是单点，要做主从、集群或改成时序数据库。最新状态可以放共享缓存或从数据库重建。

取舍上，这比单纯“主备切换”更适合水平扩展；但对当前工程原型来说，第一优先级仍然是先修指标正确性和可靠补传。

### 09. 如何扩展系统规模？

先看瓶颈在哪里，不能只按节点数拍脑袋。

计算方式是：上报 QPS 约等于 `节点数 / 采样周期`，还要乘上单条消息大小、多表写放大、MySQL 写入延迟和峰值集中程度。比如只是 10 秒周期上报，单看 RPC 请求量不一定马上需要消息队列。

扩展路径我会分三步：**接收层** 先让 Manager 无状态多实例；**写入层** 引入持久化队列做削峰，消费者水平扩展；**存储层** 做按时间分区、冷热归档，或者换时序数据库。消息队列适合数据库同步写成为瓶颈、需要削峰、需要补传持久化或多消费者处理时再引入，不是节点一多就必然要上。

## gRPC与Protobuf

### 01. 性能监控用到了grpc、protobuf，你讲一下grpc它的一个底层原理

gRPC 可以理解成“IDL + Protobuf 序列化 + HTTP/2 传输 + 生成代码”的 RPC 框架。

在这个项目里，客户端调用生成的 stub 方法，Protobuf 对请求对象做二进制序列化；gRPC message 外面还有 framing，一般包含压缩标志和消息长度；再放到 HTTP/2 DATA frame 里，通过 TCP 发送到服务端。服务端解帧、反序列化，再调用业务实现。

HTTP/2 的好处是一个 TCP 连接上可以并发承载多个逻辑 Stream，减少应用层串行等待和连接数量。但它底层仍然是 TCP，丢包时还是可能出现连接级队头阻塞，所以不能说完全互不影响。

### 02. protobuf？服务端和客户端的信息如何对齐？编码解码的过程如何对齐？

Protobuf 对齐主要靠字段编号和 wire type，不靠字段名。

序列化时，每个字段会编码成 tag 加 value，tag 里包含字段编号和 wire type。服务端或客户端解码时，根据字段编号匹配自己的 schema；遇到未知字段，通常可以忽略或保留，所以新增字段一般比较兼容。

但兼容性有规则：已经发布的字段编号不能复用；删除字段后最好用 `reserved` 保留编号；字段类型不能随便改，要考虑 wire type 和语义是否兼容。字段改名通常不影响 wire 格式，但字段编号变了就会破坏对齐。

### 03. grpc？编码解码的过程在哪里进行吗？

编码解码发生在 gRPC 框架和生成的桩代码里，业务代码基本不直接操作序列化细节。

Worker 侧调用 stub 的 `SetMonitorInfo` 时，框架把 `MonitorInfo` 序列化并封装到 HTTP/2 传输；Manager 侧收到后，gRPC 自动解码成请求对象，再进入业务方法。业务代码看到的是强类型 Protobuf 对象，而不是字节流。

## 内核模块与mmap零拷贝

### 01. 内核模块用什么代码编写的？

用 C 语言写，因为 Linux 内核本身主要是 C 运行环境，不能直接按普通用户态 C++ 程序的方式写。

这个项目的内核模块结构比较标准：模块初始化时分配共享缓冲区、注册字符设备、创建设备节点、启动高精度定时器；定时器每秒读取内核已有统计值并写入缓冲区；用户态通过字符设备 `mmap` 读取；卸载时停止定时器、注销设备并释放内存。编译产物是 `.ko`，通过 `insmod` 加载、`rmmod` 卸载。

### 02. 本来可以用proc方式获取数据，为什么要用内核模块？

结论是：生产选型里，10 秒级采样读 `/proc/stat` 通常也足够稳定，内核模块不是必须方案；项目里用内核模块主要是为了探索内核态到用户态的低复制数据通路。

`/proc` 的路径是每轮 `read()`，内核生成文本，用户态解析文本。内核模块的路径是把结构化累计值放在共享缓冲区，映射建立后用户态直接读结构体，省掉每轮文本解析和一次数据拷贝。

代价是维护成本和风险更高：模块 bug 可能影响内核稳定性，兼容不同内核版本也更麻烦。当前源码里 CPU 和 SoftIRQ 设备打不开时只是跳过对应维度，并没有完整回退到 `/proc/stat` 或 `/proc/softirqs`，所以我不会把它说成生产上更稳的方案。

### 03. 分布式linux性能监控这块，内核模块是有做一个mmap零拷贝，零拷贝这块你是怎么理解的啊？

我理解的零拷贝在这里不是“完全没有系统调用”，而是数据传输路径上少了一次拷贝。

传统 `read()` 路径是：内核里有统计数据，用户态发起 `read()`，内核把数据复制到用户缓冲区，用户程序再解析。`mmap` 路径是：先通过系统调用建立映射，把内核缓冲区对应页面映射到用户进程虚拟地址空间；映射完成后，用户态读这个地址就能看到同一组底层页面里的数据，不需要每次再把数据复制到用户缓冲区。

它解决的是数据传输成本问题，不自动解决并发快照一致性。比如内核正在更新多个字段，用户态同时读取，可能读到前后不一致的字段组合。更严谨的实现会加版本号、seqcount 或双缓冲。

### 04. 内核模块中 mmap 是怎么实现零拷贝的？

模块加载时用页对齐方式分配一块共享缓冲区，里面放 CPU 或 SoftIRQ 的结构体数组。字符设备实现 `mmap` 回调，用户态调用 `mmap()` 后，内核用 `remap_pfn_range` 把这块缓冲区对应的物理页映射到用户进程的虚拟地址范围。

映射建立后，内核定时器写这块缓冲区，用户态采集器读映射地址，双方访问的是同一组底层页面，所以没有 `read()` 路径里的“内核缓冲区复制到用户缓冲区”这一步。

源码里确实设置了 `pgprot_noncached`，但这个点不能简单解释成“普通 RAM 走缓存会读到旧数据”。普通共享内存通常依赖硬件缓存一致性；不可缓存更常见于设备内存或 MMIO 场景。项目更应该关注的是多字段快照一致性，目前没有版本号或 seqcount，这是后续要补的。

### 05. 那常用的一些零拷贝的框架，比如说市面上比较成熟的像dpdk这种用过吗？有听说过吗？

了解原理，没在这个项目里使用。

DPDK 主要提供用户态高速收发包能力，通常通过 PMD 轮询网卡队列，配合 HugePage、批量处理和 CPU 绑核，减少中断和上下文切换。它可以设计成 lockless，但不能简单说所有 DPDK 程序都无锁；它本身也不等同于完整 TCP/IP 协议栈，只是可以作为用户态协议栈的数据面基础。

这个项目是通用 Linux 性能监控，不应该接管网卡数据路径。网络指标用 TC eBPF 或 `/proc/net/dev` 已经够表达采集思路；CPU、内存、磁盘这些指标本来也不适合用 DPDK 解决。

### 06. cpu信息统计，内核模块是读取文件还是直接写的吗

不是读文件。CPU 内核模块直接读取 Linux 内核维护的 per-CPU 累计统计值，比如 user、system、idle、iowait、irq、softirq 等时间。

模块每秒把这些累计值写到共享缓冲区；用户态下一轮读取后，和上一次样本做差，再用忙碌时间差除以总时间差，算出百分比。所以内核模块负责暴露原始累计值，真正的百分比计算在用户态采集器里完成。

当前实现的一个问题是 Manager 侧默认拿 `cpu_stat(0)` 当整机 CPU，但 Worker 侧采集的是每个 CPU 核心，`cpu0` 不等于整机聚合，这会影响评分和主表展示，需要后续修成真正聚合或在内核模块里提供总行。

### 07. 写过驱动吗？内核模块的实现

这个项目里写的是字符设备形式的内核模块，算是驱动开发里的一个基础形态。

实现上分三块：第一是定时采集，用高精度定时器每秒读取 CPU 或 SoftIRQ 累计值；第二是字符设备，注册 `/dev/cpu_stat_monitor` 和 `/dev/cpu_softirq_monitor`；第三是 `mmap`，把内核缓冲区映射到用户态。

当前它不是 ring buffer，也没有读写指针和快照版本控制，更接近“单写、多读、弱一致”的监控原型。调试主要看 `dmesg` 里的加载、映射、卸载日志。

### 08. 如果想实现一个最简单的驱动，加载驱动时打印"驱动加载"信息，退出驱动时就打印"驱动卸载"信息，都需要用到哪些函数啊？描述下

最简单的内核模块需要两个函数：加载函数和卸载函数。

代码里用 `module_init` 指定加载时执行的函数，用 `module_exit` 指定卸载时执行的函数。加载函数里用 `printk` 或 `pr_info` 打“驱动加载”，卸载函数里打“驱动卸载”。还要声明 `MODULE_LICENSE("GPL")` 这类模块元信息。编译成 `.ko` 后，用 `insmod` 加载，用 `rmmod` 卸载。

### 09. 内核模块如何加载？

流程是先用内核构建系统编译出 `.ko`，然后用 `insmod xxx.ko` 加载。加载时内核执行 `module_init` 注册的初始化函数，完成设备号申请、字符设备注册、内存分配、定时器启动和设备节点创建。

验证可以看 `lsmod`、`dmesg`，以及 `/dev/cpu_stat_monitor`、`/dev/cpu_softirq_monitor` 是否存在。卸载用 `rmmod`，内核执行 `module_exit`，停止定时器、注销字符设备并释放内存。

### 10. 讲讲用c语言写的部分---内核模块

项目里主要有两个 C 内核模块。

CPU 模块从 `kcpustat_cpu` 这类内核统计里读取每个 CPU 的 user、system、idle、iowait、irq、softirq 等累计时间，每秒更新共享缓冲区。SoftIRQ 模块读取每个 CPU 上 10 类软中断计数，比如 TIMER、NET_TX、NET_RX、BLOCK、SCHED、RCU 等，也每秒更新共享缓冲区。

它们都只负责采集原始累计值，不负责最终诊断。用户态的 `cpu_stat_monitor.cpp` 和 `cpu_softirq_monitor.cpp` 负责打开设备、`mmap`、读结构体、做差值计算并填 Protobuf。

## eBPF网络采集

### 01. linux监控项目，说说使用ebpf进行网络流量统计的流程，ebpf在网络协议栈里面如何工作

流程可以分成编译、加载挂载、运行统计、用户态读取四步。

编译阶段用 clang 把 BPF C 程序编成字节码，并生成 skeleton。Worker 启动时用 libbpf 加载程序，Verifier 检查通过后，把程序挂到指定网卡的 TC ingress 和 egress。Ingress 大致在报文进入协议栈早期，egress 在报文发出前的 TC 路径。

运行时每个经过挂载点的包都会执行 BPF 程序，程序读取 `skb->ifindex` 和 `skb->len`，在 BPF map 里按 ifindex 累加收发字节数和包数。用户态周期性遍历 map，和上次值做差，算每秒速率。

这里要注意，TC eBPF 不是零成本。它虽然只统计、不改包，但每个包都会执行一次 map 查询和计数更新，高 PPS 场景下要压测开销。

### 02. linux系统监控的话，网络流量统计用的ebpf，你简单介绍一下这个ebpf它是如何实现一个网络流量统计的一个功能的

一句话：把统计逻辑放到内核网络数据路径的 TC hook 上，让包经过时就地计数。

具体就是：BPF 程序挂到成功 attach 的网卡 ingress 和 egress；每个包经过时按 ifindex 累加 bytes 和 packets；用户态定时从 BPF map 读取累计值；再用当前值减上次值，除以时间差，得到速率。

它的优势不是无条件比 `/proc/net/dev` 更省 CPU，而是统计位置更接近数据路径，后续可以扩展到接口、协议、流量方向等更细粒度维度。对于 10 秒级采样，读 `/proc/net/dev` 的开销也可能很低，所以是否用 eBPF 应该结合精度需求、内核版本、权限和压测结果判断。

### 03. 你用ebpf的这个它走的是内核协议栈吗还是什么

走的是内核协议栈，不是 DPDK 那种旁路内核。

项目里的 BPF 程序挂在 TC ingress 和 egress 上，数据包仍然按正常协议栈处理。BPF 程序只读取包长度和接口索引，累加统计后返回 `TC_ACT_OK` 放行，不做丢包、重定向或修改。

所以它适合做低侵入的监控统计，但不是接管网络协议栈，也不能说覆盖所有包；它只覆盖成功挂载的 net_device 和方向。

### 04. 看你有做这个网络流量统计，你对协议栈这块了解吗？比如内核协议栈或者其他的一些协议栈

了解基本路径。网卡驱动收包后进入内核网络栈，TC ingress 可以在比较早的位置看到 skb；之后进入网络层做 IP、路由，再到传输层 TCP/UDP，最后交给 socket。发送方向上，应用写 socket 后经过 TCP/IP 和 qdisc，TC egress 可以在发给驱动前统计。

项目里的 TC hook 挂在非 loopback 的接口上，但实际覆盖范围取决于 attach 成功的设备。容器 veth、bridge、bond、虚拟网卡这些是否覆盖，要看挂载策略，不能笼统说覆盖所有非本地流量。

另外，DPDK 属于用户态高速包处理框架，常用 PMD 轮询、HugePage 和绑核，减少中断和上下文切换；它不等于完整协议栈，和本项目这种通用服务器监控目标不一样。

### 05. eBPF 网络采集是怎么工作的？

传统方式是读 `/proc/net/dev`，拿网卡累计收发字节和包数，用户态做差算速率。eBPF 方式是把程序挂到 TC ingress/egress，包经过时直接在 BPF map 里累加。

当前源码是编译期选择：如果构建时发现 eBPF 依赖，就编译 `NetEbpfMonitor`；否则编译 `/proc/net/dev` 的 `NetMonitor`。需要注意两点：第一，eBPF 加载失败时现在只是 `loaded_ = false` 后 `UpdateOnce` 返回，没有真正运行时切到 procfs；第二，eBPF 版本算的是 bytes/sec，而 procfs 版本当前代码里除以了 1024，实际更像 KB/s，但 Manager 又按 B/s 打印和评分，这个单位不统一必须修。

## CPU监控与分析

### 01. cpu负载如何去做一个分析，怎么判断具体系统是哪里的问题

结论是：Load Average 只能说明系统排队压力，不能单独判断根因。

Linux 的 Load Average 主要统计可运行任务和不可中断睡眠任务，所以它高可能是 CPU 计算压力，也可能是 I/O 等待、锁竞争、存储阻塞或容器 CPU 配额导致。分析时我会先拿 1 分钟 load 和 CPU 核数对比，再看 CPU 使用率、iowait、进程状态和磁盘指标。

比如 load 高且 CPU 使用率也高，更像计算密集；load 高但 CPU 不高、iowait 高，要怀疑存储或网络文件系统等待；load 高同时内存紧张和 swap 活跃，要考虑换页压力。项目评分里用“核数乘 1.5”做负载归一化上限，这是经验参数，不是 Linux 固定告警标准。

### 02. cpu具体各个指标怎么去做一个分析

我会先给结论：CPU 各字段要结合看，不能单字段下结论。

`user` 高通常说明应用层计算多；`system` 高说明系统调用、内核路径或内核模块开销多；`iowait` 高表示 CPU 空闲期间有任务在等 I/O，但还要结合磁盘 util、await、队列长度和具体进程确认，不能直接认定磁盘已经打满；`irq` 和 `softirq` 高说明中断或软中断压力，需要再看 NET_RX、NET_TX、BLOCK、SCHED 等类型。

SoftIRQ 里 NET_RX/NET_TX 高通常和网络收发压力相关；BLOCK 高和块设备 I/O 相关；SCHED 高更可能反映调度器负载均衡活动增加，不能直接等同于上下文切换多。要判断上下文切换，还要看 `vmstat` 的 `cs`、`pidstat -w` 或 `perf sched`。

当前源码还有一点要如实说：Worker 采集的是每核 CPU 数据，Manager 取 `cpu_stat(0)` 当汇总值，这不是严格整机 CPU 聚合。

### 03. 有没有通过一些渠道去考虑或者了解，比如像cpu负载过高，内存可用比较少，这些情况我该怎么去优化？

我会把“监控系统自身优化”和“被监控业务优化”分开。

监控系统自身做的是低侵入采集：CPU/SoftIRQ 走内核模块加 `mmap`，网络可以走 TC eBPF 或 procfs，内存和磁盘走 procfs。这样能提供比较完整的指标链路，但当前还要修 CPU 聚合、磁盘字段解析、网络单位和 fallback，才能谈准确评估。

对被监控业务，监控系统主要提供定位线索，不直接替业务做优化。CPU 高就查热点进程、线程和调用栈；内存紧张先区分 RSS、page cache、slab、swap；iowait 高再看磁盘延迟和队列；网络软中断高再看包量、网卡队列和中断分布。优化动作可能是代码优化、限流、缓存、扩容或调整内核参数，要基于这些证据做。

## 内存监控与分析

### 01. 性能监控项目，解析/proc文件下meminfo去获取内存的一些使用情况，说说这里面有哪些资源的一些使用参数

主要关注几类字段。

`MemTotal` 是物理内存总量；`MemAvailable` 是内核估算的可用内存，通常比单纯 `MemFree` 更适合做使用率；`MemFree` 是完全空闲内存，低不一定有问题，因为 Linux 会用空闲内存做缓存。`Buffers`、`Cached` 是可回收缓存的一部分；`SwapTotal`、`SwapFree`、`SwapCached` 用来看交换分区状态；`Active`、`Inactive`、`AnonPages`、`Mapped`、`Slab` 相关字段可以帮助区分进程匿名页、文件缓存和内核对象占用。

项目里使用率按“总量减可用量”来算，这比只看 free 更符合 Linux 内存语义。

### 02. 性能监控项目，读取到了哪些内存指标，读取到之后如何去做一个分析（定位内存问题）

先看结论：当前系统能提供内存趋势和异常线索，但不能单独判定内存泄漏。

分析时我会先看使用率和 `MemAvailable`，确认是不是接近阈值；再看变化率，判断是突增还是长期缓慢增长；再结合 Swap，如果 `pswpin/pswpout` 或 swap 使用持续增长，说明内存压力更真实。

如果怀疑泄漏，下一步不是只看一条使用率曲线，而是区分增长来自进程 RSS、page cache 还是内核 slab。进程侧再看 RSS/PSS、匿名页、`smaps`、`pmap` 或 heap profiler；内核侧看 slabtop、缓存和 cgroup 指标。监控系统负责发现问题，定位还要结合这些工具。

### 03. 怎么分析这些数据呢？是只通过内存变化就推出吗？

不能只通过内存变化推出结论。

内存涨加 CPU 高，可能是业务流量上升；内存涨加 swap 活跃和磁盘 I/O 高，可能是换页压力；内存涨但主要是 Cached 增长，可能只是 page cache；内存涨在某个进程 RSS 或匿名页上，才更接近泄漏方向。

所以我的口径是：监控曲线先发现“内存压力或异常增长”，再用进程、cgroup、slab、swap in/out 和业务发布变更去确认原因。

## 磁盘与IO监控

### 01. 像负载、磁盘、内存，对这块这些指标的话你们是如何去优化的

这个项目主要做监控和负载评估，不直接替业务优化磁盘或内存。

磁盘这块设计上从 `/proc/diskstats` 读取累计读写次数、扇区数、耗时和 io time，然后做差算读写吞吐、IOPS、平均延迟和 util。评分时取所有磁盘里 util 最大值，因为一块关键盘打满就可能影响整体服务。

但当前源码的 diskstats 解析字段存在错位风险，所以我不会声称磁盘指标已经准确验证。正确做法是先按内核文档修字段映射，再用 `fio` 构造顺序读写、随机读写负载，对比 `iostat -x` 的吞吐、IOPS、await 和 util，确认口径一致后再把它作为评分输入。

## 采集优化与技术选型

### 01. 仅仅是做了一个性能的采集吗，有没有参与一些性能的优化，比如内存优化呀？

不只是把指标读出来，采集链路本身也做过一些低开销设计，但我不会说已经有生产级性能收益。

CPU 和 SoftIRQ 通过内核模块加 `mmap` 暴露结构化累计值，减少每轮 `read()` 和文本解析；网络在 eBPF 版本里挂 TC hook，包经过时直接计数；多个指标被打包成一个 Protobuf 消息一次 Push，而不是每个指标单独发。

这些是采集链路优化。至于业务内存优化、SQL 优化、应用热点优化，监控系统只提供指标和趋势，具体要结合进程级工具继续定位。

### 02. 采集的优化是怎么做的，降至毫秒级的操作

我不会直接说“降到毫秒级”，因为没有保存正式压测结果就不能给性能数字。

可以讲机制：CPU 和 SoftIRQ 用 `mmap` 让用户态直接读结构体，减少 `read()` 和文本解析；eBPF 在 TC hook 上就地累计网络包字节和包数，用户态只周期性读 map；内存、Load、磁盘这些低频指标继续用 procfs，稳定、简单、维护成本低。

验证方法应该是做 A/B：同样采样周期下对比 procfs、mmap、eBPF 路径的 CPU 占用、系统调用次数、采样延迟和对被监控负载的影响。没有这组数据时，只讲路径差异，不讲具体提升数字。

### 03. 为什么内核模块和 eBPF 混用？不全用 eBPF？

因为它们适合的采集对象不一样。

eBPF 适合已有 hook 点上的轻量事件统计，比如网络包经过 TC ingress/egress 时计数。CPU 状态和 SoftIRQ 这些指标，本来就是内核维护的累计统计值，用内核模块读取并暴露更直接；用 eBPF 重新构造一套统计反而受 hook 点、访问限制和指令限制影响。

所以项目采用混合方式：CPU/SoftIRQ 用内核模块加 `mmap`，网络用 TC eBPF 或 procfs，内存、Load、磁盘用 procfs。这个选择是为了展示不同采集路径的工程权衡，不是说所有场景都应该这样设计。

## 健康评分与变化率

### 01. 评分算法是怎么实现的？

设计上是反向归一化加权求和：资源压力越低，分数越高。

五个维度分别是 CPU、内存、Load、磁盘和网络。CPU、内存、磁盘按百分比归一化；Load 用 `load_avg_1 / (CPU核数 * 1.5)` 做经验归一化；网络按一个假设的最大带宽做归一化；最后按权重加权再乘 100，得到 0 到 100 的分数。

但我会主动说明当前实现边界：Manager 取 `cpu_stat(0)` 当 CPU 汇总，实际可能只是 cpu0；磁盘字段解析存在错位风险；eBPF 和 procfs 网络速率单位不统一。这些会影响评分可靠性，所以这个评分更像原型算法，后续 P0 是先修基础指标正确性，再谈调权重和告警阈值。

### 02. 变化率是怎么计算的？有什么用？

变化率设计上就是相邻样本的相对变化：`(当前值 - 上次值) / 上次值`。上次值为 0 时当前代码返回 0，避免除零。

它的作用是补充绝对阈值。绝对值告诉我现在是不是高，变化率告诉我是不是突然变坏。比如 CPU 从 20% 到 80%，和长期稳定在 80%，处理优先级可能不一样。

当前主表会写 CPU、Load、内存、磁盘、网络等变化率字段，异常查询主要用 CPU 和内存变化率触发突增类异常。工程风险是这些历史样本存在文件级静态 map，gRPC 并发处理多个 Worker 时缺少统一锁保护，后续应该收进 `HostManager` 状态并加锁，或者让接收后的业务处理串行化。

## 数据库设计

### 01. 数据库表为什么设计成 1 主表 + 4 详细表？

结论是为了区分概览查询和明细下钻。

主表存每次上报的汇总数据，比如 CPU、Load、内存、磁盘最大利用率、网络速率、评分和变化率，适合做“所有机器当前状态”“评分排行”“趋势概览”这类查询。

明细表存维度展开后的数据：网络按网卡拆，磁盘按设备拆，SoftIRQ 按 CPU 和类型拆，内存存更多字段。如果都塞进一张表，要么列很多，要么用 JSON 牺牲查询能力。现在的 1 主表 + 多明细表更适合面试展示数据建模思路。

不足是当前写库是同步路径，每轮新建 MySQL 连接，且主表和明细表不是一个事务；写失败也不会反馈给 Worker。这部分后续要加连接池、批量写、事务或队列解耦。

## 设计模式与工程实践

### 01. 项目中使用了哪些设计模式？

我不会硬套 GoF 模式。这个项目更准确地说用了接口抽象、运行时多态和编排器设计。

Worker 侧不同采集器都实现统一的 `MonitorInter` 接口，`MetricCollector` 持有采集器列表并逐个调用。这样新增一个采集维度，只要实现接口并注册进去，调度层不用知道底层是 procfs、mmap 还是 eBPF。

Manager 侧 gRPC 接收层通过回调把数据交给 `HostManager`，降低网络层和评分、入库逻辑的耦合。严格说，采集器列表不算标准组合模式，因为组合对象和叶子对象没有对外统一成同一种业务语义；它更像插件式采集器加聚合编排。

### 02. 线程安全如何保证？

线程安全要分已经做的和没做完整的。

已经做的是：`HostManager` 的 `host_scores_` 有 mutex，后台离线清理和查询不会直接无锁并发访问它。gRPC 接收层校验后通过回调进入业务处理。

没做完整的是：变化率计算用的 `last_perf_samples`，以及网络、SoftIRQ、内存、磁盘详情表的历史 sample，都是文件级静态 map。如果 gRPC 服务并发处理多个 Worker 上报，这些 map 有数据竞争风险。修法是把历史状态收进 `HostManager`，统一在同一把锁下更新，或者引入单消费者处理队列，让 `OnDataReceived` 串行执行。

### 03. 数据是怎么从采集到入库的？

链路是：Worker 采集，Protobuf 组装，gRPC Push，Manager 接收，评分和变化率计算，写 MySQL，最后查询。

具体到代码，Worker 的 `MonitorPusher::PushOnce` 创建 `MonitorInfo`，调用 `MetricCollector::CollectAll`，各采集器把 CPU、Load、内存、磁盘、网络、SoftIRQ、主机信息填进去。随后 Worker 调用 gRPC `SetMonitorInfo`。

Manager 的 `GrpcServerImpl::SetMonitorInfo` 校验原始数据后，通过回调进入 `HostManager::OnDataReceived`。这里计算健康分、更新最新状态、计算变化率并写主表和明细表。当前缺点是 MySQL 写失败不会改变 gRPC 返回值，Worker 可能以为端到端成功。

## 稳定性与高可用

### 01. 在这个性能监控系统里面，再稳定性方面，你是怎么涉及或考虑的？

我会先说结论：当前做了失败隔离，但还没做到高可靠。

采集侧，各维度采集器独立，一个维度失败通常只是缺该维度，不会让 Worker 主进程退出。Load 有 `/proc/loadavg` fallback；网络是编译期选择 eBPF 或 procfs；eBPF 运行时加载失败没有真正 fallback；CPU 和 SoftIRQ 设备打不开也只是跳过。

传输侧，Worker Push 失败会打印错误，下一轮继续，但没有指数退避、本地缓存和补传。Manager 侧会清理超时主机，但 Manager 自身单点，gRPC 明文，MySQL 写入每次新建连接，主表和明细表也不是事务。

并发侧，部分共享状态有锁，但变化率历史 map 没有完整保护。这些是工程原型阶段的真实不足，后续可靠性优先级应该放在指标正确性、并发状态管理、补传和写库事务上。

## 验证与测试

### 01. stress、iperf工具怎么使用的，平时还有用其他的一些验证工具吗

验证我会按指标维度做，不编造结果数字。

CPU 可以用 `stress --cpu 4` 或 `stress-ng --cpu 4` 产生 4 个 CPU worker。验证口径不是“整机一定接近 100%”，而是看 4 个逻辑 CPU 是否接近满载，或者整机平均使用率是否接近 `4 / 逻辑核数`。内存可以用 `stress --vm 2 --vm-bytes 1G --timeout 60s`，注意这通常是每个 worker 申请指定大小，验证时要看总申请量和 `MemAvailable`、RSS、swap 活动。

网络用 `iperf3`：TCP 可以 `iperf3 -s` 和 `iperf3 -c <server_ip> -t 30`；UDP 目标带宽才用 `iperf3 -c <server_ip> -u -b 200M -t 30`。对比时要统一采样窗口和单位，还要注意 iperf3 多数报告应用层吞吐，TC 统计的是 skb 字节口径，不能直接要求完全相等。

磁盘更推荐 `fio`，比如顺序写、随机读写分别构造负载，再和 `iostat -x` 对比吞吐、IOPS、await 和 util。普通 `dd` 容易受 page cache 影响，最多作为粗略功能验证。

### 02. 用过iperf吗？怎么用的？

用过，主要用于构造可控网络流量做功能性对比。

TCP 场景是服务端执行 `iperf3 -s`，客户端执行 `iperf3 -c <server_ip> -t 30`，观察监控系统的收发速率趋势是否跟 iperf3 同方向、同数量级。UDP 场景才指定目标带宽，比如 `iperf3 -c <server_ip> -u -b 200M -t 30`。

我不会说“误差 1% 或 5%”这种数字，因为没有保存正式测试报告就不能这么讲。更严谨的验证要统一 eBPF 和 procfs 的速率单位，固定采样窗口，明确比较的是应用层吞吐还是网卡/TC 字节，再跑多轮计算平均误差和最大误差。当前项目里网络单位还不统一，所以这项应该先修代码再做正式精度验证。

## 项目总结与亮点

### 01. 项目亮点有哪些？可改进的方向有哪些？

亮点我会讲三个：第一，采集路径分层，CPU/SoftIRQ 用内核模块加 `mmap`，网络支持 TC eBPF 和 procfs，内存、Load、磁盘走 procfs；第二，Worker 到 Manager 的 Protobuf + gRPC Push 主链路完整，能把多维指标落库并查询；第三，设计了五维健康评分和变化率，能把多指标压缩成负载评估结果。

改进方向要按优先级来。

**P0 是数据正确性。** 修复整机 CPU 聚合，修复 diskstats 字段解析，统一 eBPF 和 procfs 网络速率单位，明确收发变化率字段口径，并建立 stress/stress-ng、iperf3、fio、iostat 的对比验证。

**P1 是可靠性和并发。** 修复历史状态 map 的并发访问；Worker 增加本地有界缓冲或 WAL；Manager 写库加事务、连接池和批量写；实现真正运行时 fallback。

**P2 是安全和扩展。** gRPC 加 TLS/mTLS，凭据配置化，SQL 参数化，数据保留和降采样，Manager 接收层无状态多实例，再根据吞吐瓶颈决定是否引入消息队列或时序数据库。

所以这个项目准确定位是 Linux 分布式性能监控与动态负载评估工程原型，已经打通技术链路，但离生产级平台还差正确性验证、可靠性和安全治理。
