# MonitorSystem 项目面试问答（口语优化版）

> 项目定位：基于 C++17、Linux 内核模块、mmap、eBPF/TC、gRPC、Protobuf 和 MySQL 的分布式 Linux 性能监控与动态负载评估工程原型。
>
> 使用方式：优先回答正文；面试官继续追问时，再展开“追问展开”部分。不要逐字背诵，重点记住数据流、机制、取舍和当前边界。

## 项目整体与架构

### 01. 对于 Linux 分布式性能监控这个项目，在我不熟悉这个系统的情况下，你给我介绍一下这个系统

这是一个 **Worker-Agent + Manager** 架构的 Linux 分布式性能监控系统。

Worker 部署在被监控节点，默认每 10 秒采集一次 CPU、Load、内存、磁盘、网络和 SoftIRQ。CPU 与 SoftIRQ 通过内核模块加 `mmap` 采集，网络支持 TC eBPF 和 `/proc/net/dev` 两种实现，其他低频指标主要从 procfs 获取。

采集结果会被组装成 Protobuf 的 `MonitorInfo`，通过同步一元 gRPC 主动 Push 给 Manager。Manager 收到后维护主机最新状态，计算多维健康评分和相邻样本变化率，写入 MySQL，并提供趋势、异常、评分排行和指标明细等查询接口。

一句话概括就是：**Worker 负责采集和上报，Manager 负责聚合、评分、存储和查询。** 当前定位是工程原型，已经打通完整技术链路，但在数据正确性、可靠传输和高可用方面还需要继续完善。

### 02. 对于这个性能监控项目，你觉得从技术上来讲，这个系统最关键的几个点是什么

我认为有三个关键点。

**第一，内核态到用户态的数据通路。** CPU 和 SoftIRQ 由内核模块读取累计统计值，再通过字符设备 `mmap` 暴露给用户态。映射完成后，采集器不需要每轮都调用 `read()` 并解析文本。

**第二，Worker 到 Manager 的上报模型。** Worker 采集完成后主动 Push，Manager 不需要逐个维护 Worker 的访问地址，比较适合 Agent 主动上报的架构。

**第三，多维负载评估。** Manager 将 CPU、内存、Load、磁盘和网络归一化后加权，得到统一健康分，用于快速比较不同节点的整体压力。

这三个点分别对应了项目的底层采集、分布式通信和业务价值。

### 03. 为什么选择 Push 模式而不是 Pull 模式？

Push 和 Pull 都能实现秒级监控，这个项目选择 Push，主要是因为采集行为由 Worker 本地驱动。Worker 一轮采集结束后直接组装 `MonitorInfo` 并调用 Manager 的 `SetMonitorInfo`，链路比较直接。

这样 Manager 不需要保存每个 Worker 的可访问地址，Worker 扩缩容、IP 变化或者处于 NAT 后面时接入也更简单。

代价是发送失败、重试、缓存和补传需要由 Worker 侧处理。当前使用同步 gRPC，服务端变慢时会通过阻塞、超时或失败反馈压力，但 Worker 还没有完善的发送队列、退避重试和本地 WAL，因此目前属于周期上报，而不是可靠消息系统。

### 04. 性能采集这块涉及哪些模块？整体代码逻辑是怎样的？

采集链路可以分四层。

**内核模块层：** CPU 状态和 SoftIRQ 各有一个 C 内核模块，每秒读取内核累计统计值，写入共享缓冲区，并通过字符设备 `mmap` 暴露给用户态。

**eBPF 网络层：** 启用 eBPF 时，程序挂在网卡 TC ingress 和 egress，按 ifindex 累加字节数和包数，用户态读取 BPF Map 后做差计算速率。

**用户态采集器层：** CPU、Load、内存、磁盘、网络、SoftIRQ 和主机信息分别实现统一的 `MonitorInter` 接口，由 `MetricCollector` 统一调度并填充 Protobuf。

**上报层：** `MonitorPusher` 周期调用 `CollectAll`，然后通过 gRPC 将完整的 `MonitorInfo` 推给 Manager。

整体设计是：**底层负责获取原始指标，采集器负责解析和计算，调度器负责聚合，上报模块负责传输。**

### 05. 监控项目是团队项目吗？你主要负责什么？

这个项目是我独立完成的工程原型，从需求拆解、架构设计到代码实现都由我完成。

投入最多的是三部分：第一是 CPU 和 SoftIRQ 的内核模块与 `mmap` 采集；第二是 TC eBPF 网络统计；第三是 Manager 侧的评分、MySQL 入库和查询链路。

它的价值不是已经达到生产级，而是完整串联了 Linux 底层采集、C++ Agent、gRPC/Protobuf、动态评分和数据存储。

### 06. 性能监控项目你最熟悉哪个模块？

最熟的是 **Worker 采集到 Manager 入库的主链路**，其中最熟的是内核采集部分。

CPU 和 SoftIRQ 的数据流是：内核模块读取累计统计值，写入共享缓冲区；用户态打开字符设备并 `mmap`；采集器读取两次样本做差，得到 CPU 百分比或 SoftIRQ 每秒速率；随后填入 `MonitorInfo`，通过 gRPC 推送给 Manager，最后完成评分和入库。

**追问展开：** 当前共享区不是 ring buffer，也没有版本号或 seqcount，因此属于单写多读、弱一致的原型实现。更严格的方案可以增加序列号、双缓冲或 seqcount，避免读取到更新一半的快照。

### 07. 系统如何保证高可用？

当前版本做的是**基础容错和失败隔离**，还不能称为完整高可用。

Worker 中各采集器相互独立，一个维度失败通常只会缺失对应指标，不会直接拖垮整个进程；gRPC Push 失败后 Worker 不退出，下一轮继续尝试；Manager 会清理长时间没有更新的主机状态。

但 Manager 目前仍是单点，Worker 没有本地 WAL 和补传机制，MySQL 写失败也不会反馈到 Worker，通信也没有 TLS。因此当前更准确的说法是：主链路具备一定容错能力，但还缺少服务冗余、可靠投递和存储高可用。

### 08. 如果让你对当前单点 Manager 做高可用设计，你会怎么做？

我会优先把 Manager 接收层改成**无状态多实例**。

第一层，Worker 通过服务发现或负载均衡访问多个 Manager。每条样本携带 `host_id + collect_timestamp + sequence_id`，后端使用唯一键保证幂等，避免重试和补传产生重复数据。

第二层，在接收层后增加持久化消息队列，把接收、评分和入库解耦；Worker 本地增加有界 WAL，Manager 不可用时先落盘，恢复后补传。

第三层，MySQL 本身也需要主从或集群能力，最新主机状态放到共享缓存或由持久化数据重建。

这样既能解决 Manager 单点，也能支持后续水平扩展。对于当前项目，实施顺序应先做幂等、本地缓冲和可靠写入，再引入更复杂的多实例架构。

### 09. 如何扩展系统规模？

先测算瓶颈，不能只看节点数。

上报 QPS 大致是：

```text
节点数 ÷ 采样周期
```

同时还要看单条消息大小、一条上报会写多少张表、数据库写入延迟以及是否存在集中上报峰值。

扩展时我会分三层处理：接收层把 Manager 做成无状态多实例；处理层用持久化队列削峰，并让评分和入库消费者水平扩展；存储层按时间分区、做冷热归档，数据量更大时评估时序数据库。

消息队列不是节点一多就必须引入，而是在同步写库成为瓶颈，或者系统需要削峰、持久化重试和多消费者时再使用。

## gRPC 与 Protobuf

### 01. 性能监控用到了 gRPC、Protobuf，你讲一下 gRPC 的底层原理

gRPC 可以理解成 **IDL 定义 + 代码生成 + Protobuf 序列化 + HTTP/2 传输**。

客户端调用生成的 stub 方法后，请求对象先被 Protobuf 序列化；gRPC 再增加消息帧头，通常包含压缩标志和消息长度；之后放进 HTTP/2 DATA Frame，通过 TCP 发送。服务端完成解帧和反序列化，再调用对应的业务方法。

HTTP/2 可以在一个 TCP 连接上并发承载多个逻辑 Stream，减少连接数量和应用层串行等待。但底层仍然是 TCP，发生丢包时仍可能产生连接级队头阻塞。

### 02. Protobuf 服务端和客户端的信息如何对齐？编码解码如何对齐？

Protobuf 主要靠**字段编号和 wire type** 对齐，不依赖字段名。

序列化时，每个字段会被编码成 tag 和 value，tag 中包含字段编号及 wire type。解码端根据自己的 schema，用字段编号找到对应字段；遇到未知字段时通常可以跳过，因此新增字段一般具有较好的兼容性。

兼容性规则是：已经发布的字段编号不能复用，删除字段后最好使用 `reserved`，字段类型也不能随意修改。字段改名通常不影响 wire 格式，但修改字段编号会破坏兼容。

### 03. gRPC 的编码解码过程在哪里进行？

编码解码主要由 gRPC 框架和 Protobuf 生成代码完成，业务层基本不直接操作字节流。

Worker 调用 stub 的 `SetMonitorInfo` 时，框架自动序列化并封装请求；Manager 收到后自动解码成强类型的 `MonitorInfo`，再进入业务实现。因此业务代码主要处理对象，不需要手动完成网络编解码。

## 内核模块与 mmap 零拷贝

### 01. 内核模块用什么代码编写？

使用 C 语言，因为 Linux 内核主要提供 C 语言运行环境，不能像普通用户态程序一样直接使用完整 C++ 运行时。

项目中的模块初始化时分配共享缓冲区、注册字符设备、创建设备节点并启动高精度定时器；定时器周期读取内核统计值；用户态通过 `mmap` 访问；卸载时停止定时器、注销设备并释放资源。编译结果是 `.ko` 文件。

### 02. 本来可以通过 procfs 获取数据，为什么还要用内核模块？

对于 10 秒级监控，读取 `/proc/stat` 本身完全可行。项目实现内核模块，主要是为了探索一种结构化、低复制的内核态到用户态数据通路。

procfs 路径通常是每轮调用 `read()`，内核生成文本，用户态再解析；内核模块路径是将累计值写进共享缓冲区，建立 `mmap` 后，用户态可以直接读取结构体，减少重复系统调用、文本生成和解析。

代价是开发和维护成本更高，模块错误还可能影响内核稳定性。生产选型时应先做基准测试，如果收益不明显，procfs 往往是更稳妥的方案。

### 03. 你怎么理解 mmap 零拷贝？

这里的零拷贝不是“完全没有系统调用”，而是**映射建立后，读取过程中不再把数据从内核缓冲区复制到用户缓冲区**。

传统 `read()` 路径是内核准备数据，再复制到用户缓冲区。`mmap()` 会先建立虚拟地址映射，之后内核和用户态访问的是同一组底层页面，用户态可以直接读映射地址。

`mmap` 解决的是数据传输路径问题，不自动保证并发一致性。内核正在更新多个字段时，用户态可能读到不一致快照，因此更严格的实现还需要版本号、seqcount 或双缓冲。

### 04. 内核模块中 mmap 是怎么实现零拷贝的？

模块先分配页对齐的共享缓冲区，字符设备实现 `mmap` 回调。用户态调用 `mmap()` 后，内核通过 `remap_pfn_range` 将缓冲区对应的物理页映射到用户进程的虚拟地址空间。

映射完成后，内核定时器写共享区，用户态采集器读映射地址，双方访问同一组底层页面，因此省去了 `read()` 路径中的一次数据复制。

**追问展开：** 源码使用了 `pgprot_noncached`，但不能简单解释成普通 RAM 开启缓存就会读到旧数据。普通共享内存通常依赖硬件缓存一致性；当前实现更需要关注的是多字段快照一致性。

### 05. DPDK 这种零拷贝框架你了解或使用过吗？

了解原理，但这个项目没有实际使用。

DPDK 主要提供用户态高速收发包能力，通常通过 PMD 轮询网卡队列，配合 HugePage、批量处理和 CPU 绑核，减少中断和上下文切换。它可以采用无锁设计，但不能说所有 DPDK 程序都无锁；DPDK 本身也不等同于完整 TCP/IP 协议栈。

这个项目是通用服务器监控，不需要接管网卡数据路径，因此使用 TC eBPF 或 `/proc/net/dev` 更合适。

### 06. CPU 信息统计时，内核模块是读取文件还是直接读取内核数据？

不是读取文件，而是直接读取 Linux 内核维护的 per-CPU 累计统计值，例如 user、system、idle、iowait、irq 和 softirq 时间。

模块每秒把累计值写进共享缓冲区；用户态读取当前值与上一次值，用增量计算各状态占比。因此内核模块负责提供原始累计值，百分比计算在用户态完成。

**追问展开：** 当前 Worker 输出的是每个逻辑 CPU 的数据，Manager 的整机聚合逻辑还需要修正，不能直接把 `cpu0` 当成整机 CPU 使用率。

### 07. 写过驱动吗？介绍一下这个内核模块的实现

项目中实现的是字符设备形式的内核模块，可以看作驱动开发的一种基础形态。

主要分三部分：高精度定时器周期采集 CPU 或 SoftIRQ 累计值；字符设备提供 `/dev/cpu_stat_monitor` 和 `/dev/cpu_softirq_monitor`；`mmap` 回调把内核缓冲区映射到用户态。

当前实现不是 ring buffer，也没有快照版本控制，更接近单写多读、弱一致的监控原型。调试主要通过 `dmesg` 查看加载、映射和卸载日志。

### 08. 最简单的驱动加载和卸载打印，需要哪些函数？

定义一个初始化函数和一个退出函数，分别使用 `module_init` 和 `module_exit` 注册。

初始化函数中用 `pr_info` 或 `printk` 输出“驱动加载”，退出函数输出“驱动卸载”。同时声明 `MODULE_LICENSE("GPL")` 等模块信息。编译为 `.ko` 后，通过 `insmod` 加载、`rmmod` 卸载。

### 09. 内核模块如何加载？

先通过内核构建系统编译出 `.ko`，再使用 `insmod xxx.ko` 加载。内核会执行 `module_init` 注册的初始化函数，完成设备号申请、字符设备注册、缓冲区分配、定时器启动和设备节点创建。

可以通过 `lsmod`、`dmesg` 和 `/dev` 下的设备节点验证。卸载使用 `rmmod`，内核执行 `module_exit`，停止定时器、注销设备并释放资源。

### 10. 讲讲项目中用 C 语言写的内核模块

项目主要有 CPU 和 SoftIRQ 两个 C 内核模块。

CPU 模块读取每个逻辑 CPU 的 user、system、idle、iowait、irq、softirq 等累计时间；SoftIRQ 模块读取每个 CPU 上 TIMER、NET_TX、NET_RX、BLOCK、SCHED、RCU 等类型的累计次数。两个模块都每秒更新共享缓冲区。

用户态对应的 C++ 采集器负责打开设备、执行 `mmap`、读取结构体、计算增量并填充 Protobuf。也就是说，C 模块提供原始数据，C++ 层负责计算和传输。

## eBPF 网络采集

### 01. 说说 eBPF 网络流量统计的流程，它在网络协议栈中如何工作？

流程分为编译、加载、挂载、统计和读取。

BPF C 程序由 clang 编译为 BPF 字节码并生成 skeleton；Worker 使用 libbpf 加载，Verifier 检查通过后，将程序挂到指定网卡的 TC ingress 和 egress。

每个经过挂载点的数据包都会执行 BPF 程序。程序读取 `skb->ifindex` 和 `skb->len`，在 BPF Map 中按 ifindex 累加字节数和包数。用户态周期读取累计值，与上次值做差，再除以时间间隔得到速率。

TC eBPF 并不是零成本，因为程序会在每个包上运行。高 PPS 场景下需要控制 Map 操作并通过压测评估开销。

### 02. eBPF 是如何实现网络流量统计的？

核心就是把统计逻辑放到 TC Hook 上，让数据包经过时直接计数。

程序分别挂在网卡 ingress 和 egress，按接口累计 bytes 和 packets；用户态定时读取 BPF Map，对两次累计值做差，计算收发速率。

它的主要优势是可编程和统计位置灵活，可以继续扩展到接口、协议或流量方向等维度，而不是无条件比 `/proc/net/dev` 更省 CPU。

### 03. 你的 eBPF 方案走内核协议栈吗？

走内核协议栈，不是 DPDK 那种旁路内核方案。

程序挂在 TC ingress 和 egress 上，数据包仍然按照正常的 TCP/IP 协议栈处理。BPF 程序只读取接口和长度信息，完成计数后返回 `TC_ACT_OK` 放行，不修改、不丢弃也不重定向数据包。

它只能统计成功挂载的 net_device 和方向，不能笼统说覆盖系统中的所有网络流量。

### 04. 你对 Linux 网络协议栈了解多少？

接收方向上，网卡通过 DMA 把数据放到内存，驱动和 NAPI 处理后形成 skb；TC ingress 能在报文进入上层协议处理的较早阶段看到它，之后经过 IP、路由和 TCP/UDP，最后进入 socket 接收队列。

发送方向上，应用写 socket 后经过 TCP/UDP、IP、路由和 qdisc，TC egress 可以在报文交给驱动前进行统计。

容器 veth、bridge、bond 和虚拟网卡能否被统计，取决于程序实际挂载在哪些设备上。DPDK 则是用户态高速包处理框架，目标和本项目的通用服务器监控不同。

### 05. eBPF 网络采集和 `/proc/net/dev` 有什么区别？

`/proc/net/dev` 提供各网卡累计收发字节数和包数，用户态周期读取后做差；eBPF 则在 TC ingress/egress 中随包更新 BPF Map，再由用户态读取。

procfs 实现简单、兼容性好，适合常规低频监控；eBPF 可编程性更强，方便扩展更细粒度统计，但依赖内核版本、libbpf 和权限，并且存在每包执行开销。

**追问展开：** 当前项目是编译期选择两种实现，eBPF 加载失败后没有真正运行时切回 procfs；两条路径的速率单位也需要统一。这是网络采集部分需要优先修正的工程问题。

## CPU 监控与分析

### 01. CPU Load 如何分析？怎样判断系统具体哪里有问题？

Load Average 表示系统中的排队压力，不能单独用于判断根因。Linux 的 Load 主要包含可运行任务和不可中断睡眠任务，因此高 Load 既可能来自计算压力，也可能来自 I/O 阻塞、锁竞争或 CPU 配额限制。

分析时先把 1 分钟 Load 与 CPU 核数对比，再交叉看 CPU 使用率、iowait、进程状态和磁盘指标：Load 高且 CPU 也高，更像计算密集；Load 高、CPU 不高但 iowait 高，更像存储或网络文件系统等待；同时出现内存紧张和 Swap 活跃，则要考虑换页压力。

项目中的“核数 × 1.5”只是评分归一化的经验参数，不是 Linux 通用告警标准。

### 02. CPU 各个指标应该怎样分析？

CPU 指标需要组合分析。

`user` 高通常表示应用计算较多；`system` 高说明系统调用或内核路径开销较大；`iowait` 高表示 CPU 空闲期间存在等待 I/O 的任务，需要结合磁盘 `util`、`await`、队列长度和进程 I/O 确认；`irq`、`softirq` 高则说明中断处理压力增加。

SoftIRQ 中，NET_RX/NET_TX 通常与网络收发相关，BLOCK 与块设备相关，SCHED 更多反映调度器活动。判断上下文切换是否过多，还要结合 `vmstat` 的 `cs`、`pidstat -w` 或 `perf sched`。

### 03. CPU 负载过高、内存可用较少时，应该怎么优化？

监控系统负责发现和缩小问题范围，具体优化要根据根因决定。

CPU 高时先用 `top`、`pidstat`、`perf` 找到热点进程、线程和调用栈；内存紧张时区分进程 RSS、Page Cache、Slab 和 Swap；iowait 高时看磁盘延迟、队列和具体进程 I/O；网络 SoftIRQ 高时再看包量、网卡队列、中断亲和性和是否存在单核热点。

最终优化可能是算法优化、降低锁竞争、批量 I/O、缓存、限流、扩容或调整系统参数，而不是根据单一指标直接下结论。

## 内存监控与分析

### 01. `/proc/meminfo` 中有哪些重要指标？

核心字段包括：

- `MemTotal`：物理内存总量；
- `MemAvailable`：内核估算的可用内存，适合计算实际使用率；
- `MemFree`：完全空闲内存，数值低不一定有问题；
- `Buffers`、`Cached`：可回收缓存的一部分；
- `SwapTotal`、`SwapFree`、`SwapCached`：交换分区状态；
- `Active`、`Inactive`、`AnonPages`、`Mapped`、`Slab`：用于区分匿名页、文件缓存和内核对象占用。

项目使用 `(MemTotal - MemAvailable) / MemTotal` 计算使用率，比只看 `MemFree` 更符合 Linux 的内存管理方式。

### 02. 读取内存指标后，如何定位内存问题？

先看 `MemAvailable` 和使用率，确认是否真的接近压力阈值；再看趋势，区分短时突增和长期持续增长；同时观察 Swap 使用及 `pswpin/pswpout`，判断系统是否正在频繁换页。

如果怀疑泄漏，需要继续区分增长来自进程 RSS、Page Cache 还是内核 Slab。进程侧可以看 RSS/PSS、匿名页、`smaps`、`pmap` 和堆分析工具；内核侧可以看 `slabtop` 和 cgroup 指标。

因此监控系统可以发现异常趋势，但不能只靠一条内存曲线直接判定内存泄漏。

### 03. 是不是只通过内存变化就能推出问题原因？

不能。内存变化必须与其他指标交叉分析。

内存和 CPU 同时上涨，可能是业务流量增加；内存上涨、Swap 活跃并伴随磁盘 I/O，可能是换页压力；主要是 Cached 增长，可能只是 Page Cache；某个进程的 RSS 或匿名页持续增长，才更接近应用泄漏方向。

合理流程是：先由监控系统发现异常，再结合进程、cgroup、Slab、Swap 和业务变更进一步确认。

## 磁盘与 I/O 监控

### 01. 对 Load、磁盘和内存这些指标，你们如何做优化？

项目本身主要负责监控和负载评估，不直接替业务完成优化。

磁盘设计上读取 `/proc/diskstats` 的累计读写次数、扇区数、耗时和 I/O time，通过相邻样本差计算吞吐量、IOPS、平均延迟和利用率；评分时取各磁盘利用率的最大值，用于发现某一关键磁盘已经成为瓶颈。

**追问展开：** 当前源码的 diskstats 字段映射存在错位风险，需要先按内核文档修正，再使用 `fio` 构造顺序和随机 I/O，并与 `iostat -x` 的吞吐、IOPS、await 和 util 对比。指标验证正确后，才能可靠用于评分和优化判断。

## 采集优化与技术选型

### 01. 项目只是做性能采集吗？有没有做采集链路的性能优化？

除了采集指标，采集链路也做了一些低开销设计。

CPU 和 SoftIRQ 使用内核模块加 `mmap` 暴露结构化累计值，减少重复 `read()` 和文本解析；网络在 eBPF 模式下直接在 TC Hook 中计数；多个指标会组装进一个 Protobuf 消息统一上报，而不是每个指标单独建立 RPC。

这些优化针对的是监控 Agent 自身开销。至于被监控业务的内存或代码优化，系统主要提供定位依据，还需要结合进程级工具继续分析。

### 02. 采集优化是怎么做的？是否降到了毫秒级？

目前没有完整的基准测试数据，因此不能直接给出“降到毫秒级”或具体提升比例。

机制上，`mmap` 减少了重复 `read()` 和文本解析；TC eBPF 在网络数据路径上累计计数，用户态只周期读取 Map；内存、Load 和磁盘等低频指标仍使用 procfs，以保持实现简单和稳定。

要量化收益，应在相同采样周期下做 A/B 测试，对比 procfs、mmap 和 eBPF 路径的 CPU 占用、系统调用次数、采集延迟以及对业务负载的影响。在没有结果前，只说明路径优化，不编造性能数字。

### 03. 为什么内核模块和 eBPF 混用，而不是全部使用 eBPF？

因为不同指标适合不同采集方式。

网络包天然经过 TC Hook，适合使用 eBPF 做事件驱动统计；CPU 和 SoftIRQ 已经由内核维护累计统计值，用内核模块直接读取并暴露更简单；内存、Load 和磁盘通过 procfs 就能稳定获得，没必要全部下沉到内核。

因此项目选择混合采集方案，本质是根据数据来源、Hook 能力、维护成本和运行风险做权衡，而不是认为某一种技术适合所有指标。

## 健康评分与变化率

### 01. 评分算法是怎么实现的？

评分采用**反向归一化加权求和**：资源压力越大，健康分越低。

系统综合 CPU、内存、Load、磁盘和网络五个维度。CPU、内存和磁盘按照使用率归一化；Load 按 `load1 / (CPU 核数 × 1.5)` 归一化；网络按假设带宽上限归一化；最后按权重加权并乘 100，得到 0～100 分。

这个分数适合做节点快速比较和排序，但属于经验模型，不是机器学习预测。当前实现还需要先修正整机 CPU 聚合、磁盘字段解析和网络单位，基础指标准确后再校准权重和阈值。

### 02. 变化率怎么计算？有什么作用？

变化率是相邻两次采样的相对变化：

```text
(current - previous) / previous
```

上一次值为 0 时，当前代码返回 0，避免除零。

绝对阈值反映“现在是否已经过高”，变化率反映“是否正在快速恶化”。例如 CPU 从 20% 快速升到 80%，与长期稳定在 80% 的处理优先级可能不同。

**追问展开：** 当前用于保存历史样本的部分静态 Map 没有完整并发保护。更合理的做法是将状态收进 `HostManager` 并统一加锁，或者通过单消费者队列串行处理上报。

## 数据库设计

### 01. 数据库为什么设计成 1 张主表加 4 张明细表？

主要是为了区分**概览查询**和**明细下钻**。

主表保存每轮上报的汇总数据，例如 CPU、Load、内存、磁盘最大利用率、网络速率、评分和变化率，适合当前状态、趋势和排行查询。

明细表保存展开后的数据：网络按网卡、磁盘按设备、SoftIRQ 按 CPU 和类型、内存保存更多细分字段。这样常见查询只访问主表，需要定位问题时再查明细表，避免单表列数过多或依赖 JSON。

当前不足是同步写库、每轮重新建连接，并且主表与明细表没有统一事务。后续可以增加连接池、批量写入、事务和异步队列。

## 设计模式与工程实践

### 01. 项目中使用了哪些设计模式？

项目没有刻意堆叠复杂设计模式，主要使用了**接口抽象、运行时多态和统一编排**。

不同采集器都实现 `MonitorInter`，`MetricCollector` 保存采集器列表并统一调用。新增指标时，只需要实现接口并注册，调度层不需要关心底层使用 procfs、mmap 还是 eBPF。

Manager 的 gRPC 接收层通过回调把数据交给 `HostManager`，降低网络层与评分、入库逻辑的耦合。严格来说，这更接近插件式采集器和聚合编排，而不是标准组合模式。

### 02. 线程安全如何保证？

已经加锁的部分包括 Manager 的评分缓存 `host_scores_`。gRPC 接收层校验后会调用业务回调，不在接收层持有额外的数据缓存锁。

当前不完整的部分是用于计算变化率以及保存网络、内存、磁盘和 SoftIRQ 历史样本的文件级静态 Map。多个 Worker 并发上报时，这些 Map 存在数据竞争风险。

修复方式有两种：把历史状态统一放进 `HostManager` 并使用明确的锁保护；或者在 gRPC 接收后进入单消费者处理队列，串行完成评分和入库。

### 03. 数据是怎样从采集到入库的？

链路是：**采集 → Protobuf 组装 → gRPC Push → Manager 接收 → 评分与变化率 → MySQL 入库 → 查询。**

Worker 的 `MonitorPusher::PushOnce` 创建 `MonitorInfo`，调用 `MetricCollector::CollectAll`，各采集器填充不同指标，然后调用 gRPC `SetMonitorInfo`。

Manager 的 `GrpcServerImpl::SetMonitorInfo` 接收并校验数据，再通过回调进入 `HostManager::OnDataReceived`，完成评分、最新状态更新、变化率计算和主表、明细表写入。

当前 MySQL 写入失败不会改变 gRPC 的成功返回，因此 Worker 感知到的是“Manager 已接收”，不是严格的“数据已经可靠落库”。

## 稳定性与高可用

### 01. 在这个性能监控系统中，你如何考虑稳定性？

当前主要从失败隔离、传输容错和并发保护三个方面考虑。

采集侧，各采集器相互独立，一个指标失败通常不会导致 Worker 整体退出；Load 具有 procfs 回退。传输侧，Push 失败后下一轮继续尝试，Manager 会清理长时间没有更新的主机。并发侧，接收缓存和评分缓存已经使用互斥锁保护。

不足是 CPU、SoftIRQ 和 eBPF 运行时 fallback 不完整；Worker 没有退避重试、本地缓存和补传；Manager 单点；MySQL 多表写入没有事务；部分历史状态 Map 仍存在数据竞争。

因此当前实现具备基础失败隔离，但要达到高可靠，还需要补充指标正确性验证、可靠传输、并发治理和存储事务。

## 验证与测试

### 01. stress、iperf 等工具怎么使用？还用过哪些验证工具？

我会按指标分别构造可控负载，并与系统工具进行交叉验证。

CPU 可以使用 `stress-ng --cpu 4` 产生 4 个 CPU Worker，观察对应核心是否接近满载，以及整机平均使用率是否符合逻辑核数比例。内存可以使用 `stress-ng --vm 2 --vm-bytes 1G --timeout 60s`，同时观察 `MemAvailable`、进程 RSS 和 Swap 活动。

网络使用 `iperf3`：TCP 场景执行 `iperf3 -s` 和 `iperf3 -c <server_ip> -t 30`；UDP 指定目标带宽时增加 `-u -b 200M`。对比时需要统一时间窗口和单位，并区分 iperf3 的应用层吞吐与 TC 的 skb 字节口径。

磁盘更适合用 `fio` 构造顺序和随机 I/O，再与 `iostat -x` 的吞吐、IOPS、await 和 util 对比。`dd` 容易受 Page Cache 影响，只适合粗略测试。

### 02. 用过 iperf 吗？怎么用？

使用过，主要用于构造稳定网络流量，验证网络采集趋势和数量级。

TCP 测试中，服务端执行：

```bash
iperf3 -s
```

客户端执行：

```bash
iperf3 -c <server_ip> -t 30
```

UDP 场景需要指定目标带宽，例如：

```bash
iperf3 -c <server_ip> -u -b 200M -t 30
```

正式计算误差前，需要先统一 eBPF 与 procfs 的速率单位、固定采样窗口，并明确比较的是应用层吞吐还是 TC/网卡字节。目前项目只适合说做过功能性对比，不能给出没有测试报告支撑的误差数字。

## 项目总结与亮点

### 01. 项目亮点有哪些？可改进方向有哪些？

项目亮点主要有三个。

第一，采集路径比较完整：CPU 和 SoftIRQ 使用内核模块加 `mmap`，网络支持 TC eBPF 和 procfs，内存、Load 和磁盘使用 procfs。

第二，完整打通了 Worker 采集、Protobuf 组装、gRPC Push、Manager 聚合、MySQL 入库和查询链路。

第三，设计了五维健康评分和相邻样本变化率，将多种指标转换成便于排序和观察的负载评估结果。

改进方向按优先级分为三层：

**P0：数据正确性。** 修复整机 CPU 聚合、diskstats 字段解析、网络速率单位和收发字段口径，并使用 stress-ng、iperf3、fio、iostat 建立对比测试。

**P1：可靠性与并发。** 修复历史状态 Map 的并发访问；Worker 增加有界缓存或 WAL；Manager 增加事务、连接池、批量写和真正的运行时 fallback。

**P2：安全与扩展。** gRPC 增加 TLS/mTLS，凭据配置化，SQL 参数化，增加数据保留和降采样，并将 Manager 接收层改造成无状态多实例。

整体来看，这个项目的优势是贯通了 Linux 底层采集到分布式服务端处理的完整链路；当前成熟度是工程原型，下一步重点是把指标做准、把链路做可靠。
