## 一、项目概述

### 1.1 项目定位

本项目是一个**分布式 Linux 服务器性能监控系统**，采用 **Push 模式**架构，支持多台服务器的性能数据采集、存储和查询。系统基于**内核模块**和 **eBPF 技术**实现高效的系统指标采集，适用于高并发场景（如学校选课/查成绩系统）下的服务器性能评估与调度。

### 1.2 核心价值

- **高效采集**：内核模块 + eBPF 实现零拷贝、低开销的数据采集
- **全面监控**：CPU、内存、磁盘、网络、软中断等全方位指标
- **智能评分**：多维度加权评分算法，快速评估服务器健康状态
- **丰富查询**：9 个 gRPC 查询接口，支持历史数据、趋势分析、异常检测
- **数据持久化**：MySQL 存储历史数据，支持时间序列分析

### 1.3 技术栈

| 层次     | 技术选型                       |
| -------- | ------------------------------ |
| 编程语言 | C++17                          |
| RPC 框架 | gRPC + Protocol Buffers        |
| 数据采集 | Linux 内核模块 + eBPF + procfs |
| 数据库   | MySQL 8.0+                     |
| 构建系统 | CMake 3.10+                    |
| 运行平台 | Linux (内核 5.4+，eBPF 需要)   |

### 2.2 架构模式分析

#### Push 模式 vs Pull 模式

| 维度         | Push 模式（本项目）                    | Pull 模式                        |
| ------------ | -------------------------------------- | -------------------------------- |
| 数据流向     | Worker → Manager                       | Manager → Worker                 |
| Manager 负载 | 低（被动接收）                         | 高（主动轮询）                   |
| 实时性       | 高（数据变化即推送）                   | 取决于轮询间隔                   |
| 扩展性       | Worker 数量增加不影响 Manager 主动行为 | Manager 需维护轮询列表           |
| 适用场景     | 大规模集群、实时性要求高               | 小规模、Manager 需要控制采集频率 |

**本项目选择 Push 模式的理由**：

1. 降低 Manager 负载，Manager 只需被动接收数据
2. Worker 自主控制推送频率，适应不同采集需求
3. 天然支持动态扩缩容，新 Worker 直接推送即可
4. 适合大规模服务器集群场景

## 三、功能模块设计（重点）

### 3.1 数据采集模块（Worker 端）

数据采集是整个系统的核心，采用**策略模式 + 组合模式**设计。

#### 3.1.1 设计模式：策略模式（Strategy Pattern）

```
┌─────────────────────────────────────────────────────┐
│              策略模式类图                             │
├─────────────────────────────────────────────────────┤
│                                                     │
│       <<interface>>                                 │
│       MonitorInter                                  │
│   ┌──────────────────────┐                          │
│   │ + UpdateOnce()       │                          │
│   │ + Stop()             │                          │
│   └──────────┬───────────┘                          │
│              │                                      │
│     ┌────────┼────────┬──────────┬──────────┐       │
│     ▼        ▼        ▼          ▼          ▼       │
│ ┌────────┐┌────────┐┌────────┐┌────────┐┌────────┐ │
│ │CpuStat ││CpuLoad ││  Mem   ││ Disk   ││  Net   │ │
│ │Monitor ││Monitor ││Monitor ││Monitor ││Monitor │ │
│ └────────┘└────────┘└────────┘└────────┘└────────┘ │
│     │                                            │   │
│     │         ┌──────────────┐                    │   │
│     └────────?│SoftIrqMonitor│                    │   │
│               └──────────────┘                    │   │
│               ┌──────────────┐                    │   │
│               │HostInfoMonitor│                    │   │
│               └──────────────┘                    │   │
└─────────────────────────────────────────────────────┘
```

**核心接口** `MonitorInter`：

```cpp
class MonitorInter {
 public:
  virtual ~MonitorInter() {}
  virtual void UpdateOnce(monitor::proto::MonitorInfo* monitor_info) = 0;
  virtual void Stop() = 0;
};
```

**设计要点**：

- 所有监控器实现统一的 `UpdateOnce` 接口
- 通过多态实现不同采集策略的灵活切换
- 新增监控指标只需新增一个 MonitorInter 实现类

#### 3.1.2 设计模式：组合模式（Composite Pattern）

`MetricCollector` 作为组合器，管理所有监控器：

```cpp
class MetricCollector {
 public:
  void CollectAll(monitor::proto::MonitorInfo* monitor_info) {
    monitor_info->set_name(hostname_);
    for (auto& monitor : monitors_) {
      monitor->UpdateOnce(monitor_info);
    }
  }
 private:
  std::vector<std::unique_ptr<MonitorInter>> monitors_;
};
```

**设计要点**：

- `MetricCollector` 持有所有监控器的 `unique_ptr`
- 采集时遍历调用每个监控器的 `UpdateOnce`
- 编译期通过宏 `ENABLE_EBPF` 选择 NetMonitor 或 NetEbpfMonitor

#### 3.1.3 各监控器数据源与采集逻辑

| 监控器                | 数据来源                            | 采集方式               | 关键指标                                                 |
| --------------------- | ----------------------------------- | ---------------------- | -------------------------------------------------------- |
| **CpuStatMonitor**    | 内核模块 `/dev/cpu_stat_monitor`    | mmap 零拷贝            | 各核心 user/system/idle/iowait/irq/softirq 占比          |
| **CpuLoadMonitor**    | `/proc/loadavg`（后备）/ 内核模块   | 文件读取/mmap          | 1/5/15 分钟平均负载                                      |
| **CpuSoftIrqMonitor** | 内核模块 `/dev/cpu_softirq_monitor` | mmap 零拷贝            | 各 CPU 核心 10 类软中断频率                              |
| **MemMonitor**        | `/proc/meminfo`                     | 文件逐行解析           | total/free/avail/buffers/cached/active/inactive 等 19 项 |
| **DiskMonitor**       | `/proc/diskstats`                   | 文件逐行解析           | 读写速率、IOPS、延迟、利用率                             |
| **NetMonitor**        | `/proc/net/dev`                     | 文件逐行解析           | 收发速率、包数、错误/丢包统计                            |
| **NetEbpfMonitor**    | eBPF TC Hook + BPF Map              | BPF Map 查询           | 收发速率、包数（内核态采集，精度更高）                   |
| **HostInfoMonitor**   | 系统调用                            | gethostname/getifaddrs | 主机名、主网卡 IP                                        |

```
│  │cpu_stat_data │?═══════════════════?│ │ 映射区域  │ │  │
│  │(struct       │  mmap 零拷贝        │ │          │ │  │
│  │ cpu_stat[])  │                     │ └──────────┘ │  │
│  └──────────────┘                     └──────────────┘  │
│                                                         │
│  字符设备: /dev/cpu_stat_monitor                         │
└─────────────────────────────────────────────────────────┘
```

**关键技术点**：

1. **高精度定时器 (hrtimer)**：每秒触发一次，从内核 `kcpustat_cpu()` 读取 CPU 各状态累计时间
2. **字符设备 + mmap**：注册 `/dev/cpu_stat_monitor` 字符设备，通过 `mmap` 将内核内存映射到用户空间
3. **零拷贝**：用户空间直接读取内核内存，无需 `read/write` 系统调用，减少上下文切换
4. **数据一致性**：使用 `pgprot_noncached` 设置不可缓存属性，确保用户空间读到最新数据
5. **NO\_HZ 适配**：通过 `get_cpu_idle_time_us()` 和 `get_cpu_iowait_time_us()` 适配 tickless 内核

**软中断采集内核模块** (`softirq_collector.c`)：

- 同样使用 hrtimer + mmap 机制
- 数据源为 `kstat_softirqs_cpu()`，读取 10 类软中断的累计计数
- 用户空间通过时间差计算每秒软中断频率

#### 3.1.5 eBPF 网络采集机制（重点技术）

```
┌─────────────────────────────────────────────────────────┐
│           eBPF 网络采集数据流                              │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  内核空间                              用户空间          │
│                                                         │
│  ┌──────────────┐                     ┌──────────────┐  │
│  │ TC Ingress   │ 数据包进入          │ NetEbpf      │  │
│  │ Hook         │────────?            │ Monitor      │  │
│  │ (tc_ingress) │ 更新 BPF Map       │              │  │
│  └──────────────┘                     │  bpf_map_    │  │
│                                       │  lookup_elem │  │
│  ┌──────────────┐ 数据包离开          │      │       │  │
│  │ TC Egress    │────────?            │      ▼       │  │
│  │ Hook         │ 更新 BPF Map       │  计算速率    │  │
│  │ (tc_egress)  │                     │  (差值/时间) │  │
│  └──────────────┘                     └──────────────┘  │
│         │                                                │
│         ▼                                                │
│  ┌──────────────┐                                        │
│  │ BPF Map      │  key: ifindex                         │
│  │net_stats_map │  value: {rcv_bytes, rcv_packets,      │
│  │              │          snd_bytes, snd_packets}       │
│  └──────────────┘                                        │
│                                                         │
│  TC Hook 位于 L2/L3 边界，可访问完整 skb                  │
└─────────────────────────────────────────────────────────┘
```

**关键技术点**：

1. **TC (Traffic Control) Hook**：挂载在网络协议栈 L2/L3 边界，能捕获所有进出网卡的数据包
2. **BPF Hash Map**：以 `ifindex` 为 key，`net_stats` 结构为 value，存储累计收发字节数和包数
3. **原子操作**：使用 `__sync_fetch_and_add` 确保多 CPU 并发更新安全
4. **Skeleton 机制**：通过 `bpftool gen skeleton` 生成骨架代码，简化 eBPF 程序加载
5. **动态挂载**：运行时扫描 `/sys/class/net` 获取所有网卡，自动创建 clsact qdisc 并挂载 TC hook
6. **优雅降级**：eBPF 加载失败时自动回退到 `/proc/net/dev` 的 procfs 方式

```sql

  FROM_UNIXTIME(FLOOR(UNIX_TIMESTAMP(timestamp) / interval) * interval) as time_bucket,
  AVG(cpu_percent), AVG(mem_used_percent), ...
FROM server_performance 
WHERE server_name = ? AND timestamp BETWEEN ? AND ?
GROUP BY server_name, time_bucket 
ORDER BY time_bucket
```

**设计理由**：通过时间桶聚合，将高频数据降采样为低频趋势数据，减少数据量同时保留趋势特征。

### 4.2 关键实现细节

#### 4.2.1 内核模块与用户空间的数据交互

**mmap 零拷贝机制**：

1. 内核模块使用 `__get_free_pages` 分配物理连续内存
2. 注册字符设备，实现 `mmap` 文件操作
3. `mmap` 回调中通过 `remap_pfn_range` 将内核物理内存映射到用户空间
4. 用户空间直接通过指针访问内核数据，无需 `read/write` 系统调用

**数据一致性保证**：

- 使用 `pgprot_noncached` 禁用缓存，确保每次读取都是最新值
- 内核侧 hrtimer 每秒更新，用户侧每 10 秒采样

#### 4.2.2 eBPF 程序生命周期管理

1. **编译**：Clang 编译 `net_stats.bpf.c` 为 BPF 字节码
2. **Skeleton 生成**：`bpftool gen skeleton` 生成 `net_stats.skel.h`
3. **加载**：`net_stats_bpf__open()` + `net_stats_bpf__load()`
4. **挂载**：为每个网卡创建 clsact qdisc，附加 TC ingress/egress hook
5. **数据读取**：`bpf_map_get_next_key` + `bpf_map_lookup_elem` 遍历 BPF Map
6. **卸载**：`bpf_tc_detach` + `net_stats_bpf__destroy`

#### 4.2.3 变化率计算策略

```
当前采样值 - 上次采样值
───────────────────── = 变化率
    上次采样值
```

**特殊情况处理**：

- 上次值为 0：返回 0（避免除零）
- 计数器溢出：eBPF 中检测差值为负时使用当前值
- 首次采集：无法计算变化率，设为 0

#### 4.2.4 线程模型


## 五、各功能点详细实现思路与代码评述

> 本章对每个功能点的实现过程进行逐步拆解，给出关键代码片段及设计评述。

### 5.1 功能点一：策略模式抽象接口 — MonitorInter

**实现思路**：所有监控器必须实现统一接口，使得 `MetricCollector` 可以用同一种方式调度所有采集器，无需关心底层差异。

**关键代码**：

```cpp
// worker/include/monitor/monitor_inter.h
class MonitorInter {
 public:
  MonitorInter() {}
  virtual ~MonitorInter() {}
  virtual void UpdateOnce(monitor::proto::MonitorInfo* monitor_info) = 0;
  virtual void Stop() = 0;
};
```

**评述**：

- `UpdateOnce` 接收 `MonitorInfo*` 指针，各监控器向其中填充自己负责的字段，这是一种**收集器模式**——每个监控器只关心自己负责的 `repeated` 或 `optional` 字段
- `Stop()` 提供资源释放入口，eBPF 监控器需要在此处卸载 BPF 程序
- 虚析构函数确保通过基类指针释放时调用正确的派生类析构
- **不足**：缺少错误码返回机制，当前采集失败时静默跳过，上层无法感知

***

### 5.2 功能点二：组合模式采集器 — MetricCollector

**实现思路**：在构造时注册所有监控器，采集时统一遍历调用。

**关键代码**：

```cpp
// worker/src/monitor/metric_collector.cpp
MetricCollector::MetricCollector() {
  char hostname[256];
  if (gethostname(hostname, sizeof(hostname)) == 0) {
    hostname_ = hostname;
  } else {
    hostname_ = "unknown";
  }

  monitors_.push_back(std::make_unique<CpuLoadMonitor>());
  monitors_.push_back(std::make_unique<CpuStatMonitor>());
  monitors_.push_back(std::make_unique<CpuSoftIrqMonitor>());
  monitors_.push_back(std::make_unique<MemMonitor>());
#ifdef ENABLE_EBPF
  monitors_.push_back(std::make_unique<NetEbpfMonitor>());
#else
  monitors_.push_back(std::make_unique<NetMonitor>());

  monitors_.push_back(std::make_unique<DiskMonitor>());
```

**评述**：

- `unique_ptr` 管理监控器生命周期，自动释放资源
- `#ifdef ENABLE_EBPF` 编译期选择网络监控策略，零运行时开销
- `CollectAll` 的调用顺序无关紧要，因为每个监控器操作 `MonitorInfo` 的不同字段
- **改进方向**：可改为运行时注册（`RegisterMonitor`），支持动态加载/卸载监控器

### 5.3 功能点三：CPU 状态采集 — CpuStatMonitor（内核模块 + mmap）

**实现思路**：用户空间通过 `open` 打开内核模块创建的字符设备，再通过 `mmap` 将内核内存映射到用户空间，直接读取 CPU 各核心的累计时间统计，通过两次采样的差值计算使用率。

**关键代码**：

```cpp
// worker/src/monitor/cpu_stat_monitor.cpp
void CpuStatMonitor::UpdateOnce(monitor::proto::MonitorInfo* monitor_info) {
    int fd = open("/dev/cpu_stat_monitor", O_RDONLY);
    if (fd < 0) return;  // 内核模块未加载，静默跳过

    size_t stat_count = 128;
    size_t stat_size = sizeof(struct cpu_stat) * stat_count;
    void* addr = mmap(nullptr, stat_size, PROT_READ, MAP_SHARED, fd, 0);
    if (addr == MAP_FAILED) { close(fd); return; }

    struct cpu_stat* stats = static_cast<struct cpu_stat*>(addr);
    for (size_t i = 0; i < stat_count; ++i) {
        if (stats[i].cpu_name[0] == '\0') break;  // 数组结束标记

        auto it = cpu_stat_map_.find(stats[i].cpu_name);
        if (it != cpu_stat_map_.end()) {
            struct CpuStat old = it->second;

            // 计算总时间差
            float new_total = stats[i].user + stats[i].system + stats[i].idle +
                stats[i].nice + stats[i].iowait + stats[i].irq +
                stats[i].softirq + stats[i].steal;
            float old_total = old.user + old.system + old.idle + old.nice +
                old.io_wait + old.irq + old.soft_irq + old.steal;

            // 计算忙碌时间差
            float new_busy = stats[i].user + stats[i].system +
                stats[i].nice + stats[i].irq + stats[i].softirq + stats[i].steal;
            float old_busy = old.user + old.system + old.nice +
                old.irq + old.soft_irq + old.steal;

            // 各指标百分比 = 该指标增量 / 总时间增量 * 100
            float delta_total = new_total - old_total;
            auto cpu_stat_msg = monitor_info->add_cpu_stat();
            cpu_stat_msg->set_cpu_percent(
                (new_busy - old_busy) / delta_total * 100.0f);
            cpu_stat_msg->set_usr_percent(
                (stats[i].user - old.user) / delta_total * 100.0f);
            // ... 其他指标同理
        }
        // 缓存本次采样值，供下次计算差值
        CpuStat& cached = cpu_stat_map_[stats[i].cpu_name];
        cached.user = stats[i].user;
        cached.system = stats[i].system;
        // ...
    }

    munmap(addr, stat_size);
    close(fd);
}
```

**评述**：

- **差值法计算使用率**：CPU 时间是累计值，必须通过两次采样差值才能算出区间使用率。这是所有 CPU 监控工具（top、vmstat 等）的基本原理
- `cpu_stat_map_` 缓存上次采样值，key 为 CPU 名称（如 "cpu0"），支持多核
- 首次采样时 `cpu_stat_map_` 为空，无法计算百分比，跳过输出——这是正确行为，因为第一次没有参考基线
- `mmap` 后必须 `munmap`，`open` 后必须 `close`，当前代码在异常路径上有资源泄漏风险（如 `add_cpu_stat` 抛异常时）
- **改进**：可用 RAII 封装 fd 和 mmap 区域

### 5.4 功能点四：CPU 负载采集 — CpuLoadMonitor（后备方案设计）

**实现思路**：优先从内核模块读取，失败则回退到 `/proc/loadavg`，实现优雅降级。

**关键代码**：

```cpp
// worker/src/monitor/cpu_load_monitor.cpp
void CpuLoadMonitor::UpdateOnce(monitor::proto::MonitorInfo* monitor_info) {
    // 优先尝试内核模块
    int fd = open("/dev/cpu_load_monitor", O_RDONLY);
    if (fd >= 0) {
        size_t load_size = sizeof(struct cpu_load);
        void* addr = mmap(nullptr, load_size, PROT_READ, MAP_SHARED, fd, 0);
        if (addr != MAP_FAILED) {
            struct cpu_load info;
            memcpy(&info, addr, load_size);  // 拷贝而非直接使用指针
            auto cpu_load_msg = monitor_info->mutable_cpu_load();
            cpu_load_msg->set_load_avg_1(info.load_avg_1);
            cpu_load_msg->set_load_avg_3(info.load_avg_3);
            cpu_load_msg->set_load_avg_15(info.load_avg_15);
            munmap(addr, load_size);
            close(fd);
            return;
        }
        close(fd);
    }

    // 后备方案：/proc/loadavg
    float load1, load3, load15;
    if (ReadLoadFromProc(&load1, &load3, &load15)) {
        auto cpu_load_msg = monitor_info->mutable_cpu_load();
        cpu_load_msg->set_load_avg_1(load1);
        cpu_load_msg->set_load_avg_3(load3);
        cpu_load_msg->set_load_avg_15(load15);
    }
}
```

**评述**：

- **优雅降级**是本项目的核心设计理念之一：内核模块是可选依赖，不是必须的
- `memcpy` 而非直接使用映射指针——因为数据量极小（3 个 float），拷贝开销可忽略，且避免指针悬挂
- `/proc/loadavg` 是 Linux 标准接口，所有发行版都支持，是最可靠的后备方案
- `ReadLoadFromProc` 使用 `fscanf` 直接解析，比 `ifstream` 更轻量

### 5.5 功能点五：软中断采集 — CpuSoftIrqMonitor（频率计算）

**实现思路**：从内核模块 mmap 读取软中断累计计数，通过两次采样差值除以时间差，计算每秒软中断频率。

**关键代码**：

```cpp
// worker/src/monitor/cpu_softirq_monitor.cpp
void CpuSoftIrqMonitor::UpdateOnce(monitor::proto::MonitorInfo* monitor_info) {
    int fd = open("/dev/cpu_softirq_monitor", O_RDONLY);
    if (fd < 0) return;

    size_t map_size = sizeof(struct softirq_stat) * MAX_CPUS;
    void* addr = mmap(nullptr, map_size, PROT_READ, MAP_SHARED, fd, 0);
    if (addr == MAP_FAILED) { close(fd); return; }

    struct softirq_stat* stats = static_cast<struct softirq_stat*>(addr);
    auto now = std::chrono::steady_clock::now();

    for (size_t i = 0; i < MAX_CPUS; ++i) {
        if (stats[i].cpu_name[0] == '\0') break;

        std::string cpu_name(stats[i].cpu_name);
        auto it = cpu_softirqs_.find(cpu_name);
        auto* softirq_msg = monitor_info->add_soft_irq();
        softirq_msg->set_cpu(cpu_name);

        if (it != cpu_softirqs_.end()) {
            // 计算时间差（秒）
            double seconds = std::chrono::duration_cast<
                std::chrono::milliseconds>(now - it->second.timepoint).count() / 1000.0;

            if (seconds > 0) {
                // 频率 = (当前累计值 - 上次累计值) / 时间差
                softirq_msg->set_hi(
                    static_cast<int64_t>((stats[i].hi - it->second.hi) / seconds));
                softirq_msg->set_timer(
                    static_cast<int64_t>((stats[i].timer - it->second.timer) / seconds));
                // ... 其他 8 类软中断同理
            }
        }
        // 缓存当前采样
        SoftIrq& cached = cpu_softirqs_[cpu_name];
        cached.hi = stats[i].hi;
        cached.timepoint = now;
        // ...
    }
    munmap(addr, map_size);
    close(fd);
}
```

**评述**：

- **累计值 → 频率的转换**：内核模块提供的是软中断的累计触发次数，用户空间需要通过差值/时间计算每秒频率，这是监控系统的常见模式
- 使用 `steady_clock` 而非 `system_clock`——前者不受系统时间调整影响，适合计算时间差
- 软中断频率数据对网络调优至关重要：`NET_RX`/`NET_TX` 高可能意味着网络负载重，`SCHED` 高可能意味着上下文切换频繁
- **与 CPU 状态采集的区别**：CPU 状态计算的是百分比（增量/总增量），软中断计算的是绝对频率（增量/时间）

***

### 5.6 功能点六：内存采集 — MemMonitor（/proc/meminfo 解析）

**实现思路**：逐行读取 `/proc/meminfo`，按字段名匹配解析，单位从 kB 转换为 GB。

**关键代码**：

```cpp
// worker/src/monitor/mem_monitor.cpp
void MemMonitor::UpdateOnce(monitor::proto::MonitorInfo* monitor_info) {
    ReadFile mem_file("/proc/meminfo");
    struct MenInfo mem_info;
    std::vector<std::string> mem_datas;
    while (mem_file.ReadLine(&mem_datas)) {
        if (mem_datas[0] == "MemTotal:") {
            mem_info.total = std::stoll(mem_datas[1]);
        } else if (mem_datas[0] == "MemFree:") {
            mem_info.free = std::stoll(mem_datas[1]);
        } else if (mem_datas[0] == "MemAvailable:") {
            mem_info.avail = std::stoll(mem_datas[1]);
        }
        // ... 其余 16 个字段同理
        mem_datas.clear();
    }

    auto mem_detail = monitor_info->mutable_mem_info();
    mem_detail->set_used_percent(
        (mem_info.total - mem_info.avail) * 1.0 / mem_info.total * 100.0);
    mem_detail->set_total(mem_info.total / KBToGB);  // KB → GB
    mem_detail->set_free(mem_info.free / KBToGB);
    // ...
}
```

**评述**：

- **使用率计算**：`(total - avail) / total` 而非 `(total - free) / total`——因为 Linux 的 `free` 不包含 buffers/cached，而 `avail` 包含了可回收的缓存，更能反映真实可用内存
- `KBToGB = 1000 * 1000`：使用 10^3 进制而非 2^10，与 `free -h` 命令一致
- `ReadFile` 是自定义的文件读取工具类，封装了 `std::ifstream` 的逐行读取和按空白分割
- **改进方向**：可用 `unordered_map` 替代 if-else 链，提高可读性和扩展性

### 5.7 功能点七：磁盘采集 — DiskMonitor（/proc/diskstats 解析 + 速率计算）

**实现思路**：读取 `/proc/diskstats` 获取磁盘累计 I/O 统计，通过两次采样差值计算读写速率、IOPS、延迟和利用率。

**关键代码**：

```cpp
// worker/src/monitor/disk_monitor.cpp
void DiskMonitor::UpdateOnce(monitor::proto::MonitorInfo* monitor_info) {
    std::ifstream ifs("/proc/diskstats");
    std::string line;
    double now = ::time(nullptr);

    while (std::getline(ifs, line)) {
        std::istringstream iss(line);
        int major, minor;
        std::string name;
        DiskSample curr{};
        iss >> major >> minor >> name >> curr.reads >> curr.writes >>
            curr.sectors_read >> curr.sectors_written >> curr.read_time_ms >>
            curr.write_time_ms >> curr.io_in_progress >> curr.io_time_ms >>
            curr.weighted_io_time_ms;

        // 跳过虚拟盘
        if (name.find("loop") == 0 || name.find("ram") == 0) continue;

        auto* disk = monitor_info->add_disk_info();
        disk->set_name(name);
        disk->set_reads(curr.reads);
        // ... 原始计数器

        auto it = last_samples.find(name);
        double dt = now - last_time[name];
        if (it != last_samples.end() && dt > 0) {
            const auto& last = it->second;
            double read_bytes = (curr.sectors_read - last.sectors_read) * 512.0;
            double write_bytes = (curr.sectors_written - last.sectors_written) * 512.0;

            disk->set_read_bytes_per_sec(read_bytes / dt);
            disk->set_write_bytes_per_sec(write_bytes / dt);
            disk->set_read_iops((curr.reads - last.reads) / dt);
            disk->set_write_iops((curr.writes - last.writes) / dt);
            disk->set_avg_read_latency_ms(
                read_ios > 0 ? read_time / read_ios : 0);
            disk->set_util_percent(io_time / (dt * 10.0));
        }
        last_samples[name] = curr;
        last_time[name] = now;
    }
}
```

**评述**：

- **扇区大小 512 字节**：`sectors_read * 512` 转换为字节数，这是 Linux 内核的约定
- **磁盘利用率计算**：`io_time / (dt * 10.0)`——`io_time_ms` 单位是毫秒，`dt` 单位是秒，`dt * 1000` 转为毫秒，再除以 100 得到百分比，即 `io_time / (dt * 1000) * 100 = io_time / (dt * 10)`
- **平均延迟计算**：`read_time / read_ios`——读 I/O 总耗时 / 读 I/O 次数 = 平均每次读延迟
- **过滤虚拟盘**：`loop` 和 `ram` 设备无实际监控价值
- **不足**：`last_samples` 和 `last_time` 使用 `static` 全局变量，不支持多实例

***

### 5.8 功能点八：网络采集（procfs 方式）— NetMonitor

**实现思路**：解析 `/proc/net/dev`，通过两次采样差值计算收发速率。

**关键代码**：

```cpp
// worker/src/monitor/net_monitor.cpp
static std::vector<NetStat> get_net_stats_from_proc() {
    std::vector<NetStat> stats;
    std::ifstream file("/proc/net/dev");
    std::string line;
    std::getline(file, line);  // 跳过标题行1
    std::getline(file, line);  // 跳过标题行2

    while (std::getline(file, line)) {
        std::istringstream iss(line);
        std::string iface;
        iss >> iface;
        if (iface.back() == ':') iface.pop_back();  // "eth0:" → "eth0"
        if (iface == "lo") continue;                 // 跳过回环

        NetStat stat;
        stat.name = iface;
        iss >> stat.rcv_bytes >> stat.rcv_packets >> stat.err_in >> stat.drop_in;
        uint64_t dummy;
        iss >> dummy >> dummy >> dummy >> dummy;  // fifo frame compressed multicast
        iss >> stat.snd_bytes >> stat.snd_packets >> stat.err_out >> stat.drop_out;
        stats.push_back(stat);
    }
    return stats;
}

void NetMonitor::UpdateOnce(monitor::proto::MonitorInfo* monitor_info) {
    auto now = std::chrono::steady_clock::now();
    auto stats = get_net_stats_from_proc();

    for (const auto& stat : stats) {
        auto it = last_net_info_.find(stat.name);
        double rcv_rate = 0, send_rate = 0;

        if (it != last_net_info_.end()) {
            double dt = std::chrono::duration<double>(now - it->second.timepoint).count();
            if (dt > 0) {
                rcv_rate = (stat.rcv_bytes - it->second.rcv_bytes) / 1024.0 / dt;
                send_rate = (stat.snd_bytes - it->second.snd_bytes) / 1024.0 / dt;
            }
        }

        auto net_info = monitor_info->add_net_info();
        net_info->set_name(stat.name);
        net_info->set_rcv_rate(rcv_rate);       // KB/s
        net_info->set_send_rate(send_rate);     // KB/s
        net_info->set_err_in(stat.err_in);
        net_info->set_drop_in(stat.drop_in);
        // ...
    }
}
```

**评述**：

- `/proc/net/dev` 格式固定：接口名后跟 16 个接收统计和 8 个发送统计
- 速率单位为 KB/s（`/ 1024.0`），与 `ifconfig`/`nload` 等工具一致
- `err_in`/`err_out`/`drop_in`/`drop_out` 是累计值，非速率——在 Manager 端会计算变化率
- 跳过 `lo` 回环接口，避免统计无意义的本地回环流量

### 5.9 功能点九：网络采集（eBPF 方式）— NetEbpfMonitor

**实现思路**：加载 eBPF 程序到内核，通过 TC Hook 在每个数据包经过时更新 BPF Map，用户空间定期遍历 Map 读取累计值并计算速率。

**关键代码（eBPF 内核程序）**：

```c
// worker/src/ebpf/net_stats.bpf.c
struct net_stats {
    __u64 rcv_bytes;
    __u64 rcv_packets;
    __u64 snd_bytes;
    __u64 snd_packets;
};

struct {
    __uint(type, BPF_MAP_TYPE_HASH);
    __uint(max_entries, 64);
    __type(key, __u32);             // ifindex
    __type(value, struct net_stats);
} net_stats_map SEC(".maps");

static __always_inline void update_stats(__u32 ifindex, __u32 len, bool is_rx) {
    struct net_stats *stats = bpf_map_lookup_elem(&net_stats_map, &ifindex);
    if (!stats) {
        struct net_stats new_stats = {};
        if (is_rx) { new_stats.rcv_bytes = len; new_stats.rcv_packets = 1; }
        else       { new_stats.snd_bytes = len; new_stats.snd_packets = 1; }
        bpf_map_update_elem(&net_stats_map, &ifindex, &new_stats, BPF_ANY);
    } else {
        if (is_rx) {
            __sync_fetch_and_add(&stats->rcv_bytes, len);
            __sync_fetch_and_add(&stats->rcv_packets, 1);
        } else {
            __sync_fetch_and_add(&stats->snd_bytes, len);
            __sync_fetch_and_add(&stats->snd_packets, 1);
        }
    }
}

SEC("tc/ingress")
int tc_ingress(struct __sk_buff *skb) {
    update_stats(skb->ifindex, skb->len, true);
    return TC_ACT_OK;  // 不影响数据包，仅统计
}

SEC("tc/egress")
int tc_egress(struct __sk_buff *skb) {
    update_stats(skb->ifindex, skb->len, false);
    return TC_ACT_OK;
}
```

**关键代码（用户空间加载与读取）**：

```cpp
// worker/src/monitor/net_ebpf_monitor.cpp
bool NetEbpfMonitor::InitEbpf() {
    struct net_stats_bpf* skel = net_stats_bpf__open();
    if (!skel) return false;

    int err = net_stats_bpf__load(skel);
    if (err) { net_stats_bpf__destroy(skel); return false; }

    map_fd_ = bpf_map__fd(skel->maps.net_stats_map);

    // 为每个网卡附加 TC hook
    auto ifindexes = GetAllIfIndexes();
    int ingress_fd = bpf_program__fd(skel->progs.tc_ingress);
    int egress_fd = bpf_program__fd(skel->progs.tc_egress);

    for (uint32_t ifindex : ifindexes) {
        char ifname[IF_NAMESIZE];
        if (if_indextoname(ifindex, ifname) == nullptr) continue;
        if (strcmp(ifname, "lo") == 0) continue;

        tc_qdisc_create_clsact(ifindex);  // 创建 clsact qdisc

        // 附加 ingress
        LIBBPF_OPTS(bpf_tc_hook, hook, .ifindex = ifindex,
                    .attach_point = BPF_TC_INGRESS);
        bpf_tc_hook_create(&hook);
        LIBBPF_OPTS(bpf_tc_opts, opts_in, .prog_fd = ingress_fd);
        bpf_tc_attach(&hook, &opts_in);

        // 附加 egress
        hook.attach_point = BPF_TC_EGRESS;
        LIBBPF_OPTS(bpf_tc_opts, opts_eg, .prog_fd = egress_fd);
        bpf_tc_attach(&hook, &opts_eg);
    }
    bpf_obj_ = reinterpret_cast<struct bpf_object*>(skel);
    return true;
}

void NetEbpfMonitor::UpdateOnce(monitor::proto::MonitorInfo* monitor_info) {
    uint32_t key = 0, next_key;
    struct net_stats stats;

    while (bpf_map_get_next_key(map_fd_, &key, &next_key) == 0) {
        if (bpf_map_lookup_elem(map_fd_, &next_key, &stats) == 0) {
            std::string ifname = GetIfName(next_key);
            auto cache_it = cache_.find(next_key);
            if (cache_it != cache_.end()) {
                const auto& old = cache_it->second;
                auto duration = std::chrono::duration_cast<std::chrono::milliseconds>(
                    now - old.timestamp).count();
                if (duration > 0) {
                    int64_t rcv_diff = stats.rcv_bytes - old.rcv_bytes;
                    if (rcv_diff < 0) rcv_diff = stats.rcv_bytes;  // 溢出处理
                    net_info->set_rcv_rate(rcv_diff * 1000 / duration);
                    // ...
                }
            }
            cache_[next_key] = {stats.rcv_bytes, stats.rcv_packets,
                                stats.snd_bytes, stats.snd_packets, now};
        }
        key = next_key;
    }
}
```

**评述**：

- **eBPF vs procfs 的核心区别**：procfs 是内核定时汇总的快照，eBPF 是每个数据包经过时的实时统计，精度更高
- `__sync_fetch_and_add` 是 GCC 内置原子操作，确保多 CPU 并发更新 BPF Map 安全
- `TC_ACT_OK` 返回值表示放行数据包，不修改不丢弃——这是"旁路监控"的核心
- **计数器溢出处理**：`if (rcv_diff < 0) rcv_diff = stats.rcv_bytes`——当计数器回绕时，使用当前值作为近似
- **Skeleton 机制**：`net_stats_bpf__open/load/destroy` 是 `bpftool gen skeleton` 自动生成的，简化了 eBPF 程序的生命周期管理
- **clsact qdisc**：TC hook 的前置条件，必须在网卡上创建 clsact qdisc 才能挂载 BPF 程序

```cpp
// worker/src/monitor/host_info_monitor.cpp
std::string HostInfoMonitor::GetPrimaryIpAddress() {
    struct ifaddrs* ifaddr;
    if (getifaddrs(&ifaddr) == -1) return "";

    for (struct ifaddrs* ifa = ifaddr; ifa != nullptr; ifa = ifa->ifa_next) {
        if (ifa->ifa_addr == nullptr) continue;
        if (ifa->ifa_addr->sa_family != AF_INET) continue;  // 仅 IPv4
        if (strcmp(ifa->ifa_name, "lo") == 0) continue;     // 跳过回环

        // 跳过虚拟网卡
        std::string ifname(ifa->ifa_name);
        if (ifname.find("docker") == 0 || ifname.find("veth") == 0 ||
            ifname.find("br-") == 0 || ifname.find("virbr") == 0) continue;

        struct sockaddr_in* addr = reinterpret_cast<struct sockaddr_in*>(ifa->ifa_addr);
        char ip_str[INET_ADDRSTRLEN];
        if (inet_ntop(AF_INET, &(addr->sin_addr), ip_str, sizeof(ip_str)) != nullptr) {
            freeifaddrs(ifaddr);
            return ip_str;  // 返回第一个有效 IP
        }
    }
    freeifaddrs(ifaddr);
    return "";
}
```

### 5.13 功能点十三：健康评分算法 — HostManager::CalcScore

**实现思路**：将多维指标反向归一化后加权求和，分数越高表示服务器越健康。

**关键代码**：

```cpp
// manager/src/host_manager.cpp
double HostManager::CalcScore(const monitor::proto::MonitorInfo& info) {
    const double cpu_weight = 0.35;
    const double mem_weight = 0.30;
    const double load_weight = 0.15;
    const double disk_weight = 0.15;
    const double net_weight = 0.05;
    const double load_coefficient = 1.5;
    const double max_bandwidth = 125000000.0;  // 1Gbps

    double cpu_percent = 0, load_avg_1 = 0, mem_percent = 0;
    double net_recv_rate = 0, net_send_rate = 0, disk_util = 0;
    int cpu_cores = 1;

    if (info.cpu_stat_size() > 0) {
        cpu_percent = info.cpu_stat(0).cpu_percent();
        cpu_cores = info.cpu_stat_size() - 1;  // 第0个是总CPU
        if (cpu_cores < 1) cpu_cores = 1;
    }
    if (info.has_cpu_load()) load_avg_1 = info.cpu_load().load_avg_1();
    if (info.has_mem_info()) mem_percent = info.mem_info().used_percent();
    if (info.net_info_size() > 0) {
        net_recv_rate = info.net_info(0).rcv_rate();
        net_send_rate = info.net_info(0).send_rate();
    }
    if (info.disk_info_size() > 0) {
        for (int i = 0; i < info.disk_info_size(); ++i) {
            double util = info.disk_info(i).util_percent();
            if (util > disk_util) disk_util = util;  // 取最大值
        }
    }

    auto clamp = [](double v) { return v < 0 ? 0 : (v > 1 ? 1 : v); };

    double cpu_score = clamp(1.0 - cpu_percent / 100.0);
    double mem_score = clamp(1.0 - mem_percent / 100.0);
    double load_score = clamp(1.0 - load_avg_1 / (cpu_cores * load_coefficient));
    double disk_score = clamp(1.0 - disk_util / 100.0);
    double net_recv_score = clamp(1.0 - net_recv_rate / max_bandwidth);
    double net_send_score = clamp(1.0 - net_send_rate / max_bandwidth);
    double net_score = (net_recv_score + net_send_score) / 2.0;

    double score = cpu_score * cpu_weight + mem_score * mem_weight +
                   load_score * load_weight + disk_score * disk_weight +
                   net_score * net_weight;
    score *= 100.0;
    return score < 0 ? 0 : (score > 100 ? 100 : score);
}
```

**评述**：

- **反向归一化**：使用率越低 → 分数越高 → 服务器越健康 → 越适合接收请求
- **clamp 函数**：防止异常值（如 CPU 使用率 > 100% 或 < 0%）导致分数越界
- **负载归一化**：`load_avg_1 / (cpu_cores * 1.5)`——负载除以 CPU 核心数的 1.5 倍，因为 I/O 密集型场景下负载可以超过核心数
- **磁盘利用率取最大值**：任何一块磁盘成为瓶颈都会影响整体性能
- **网络评分取收发均值**：收发对称考虑
- **cpu\_cores 计算**：`cpu_stat_size() - 1` 因为第一个元素是所有 CPU 的汇总

### 5.14 功能点十四：变化率计算 — HostManager::OnDataReceived

**实现思路**：每次收到数据时，与上次采样值比较，计算各指标的变化率。

**关键代码**：


```c
        kcs = &kcpustat_cpu(cpu);
        snprintf(cpu_stat_data[idx].cpu_name, 16, "cpu%d", cpu);

        cpu_stat_data[idx].user = nsec_to_jiffies(kcs->cpustat[CPUTIME_USER]);
        cpu_stat_data[idx].idle = cpu_stat_get_idle_time(cpu);  // 适配 NO_HZ
        // ...
        idx++;
    }
    if (idx < MAX_CPUS) cpu_stat_data[idx].cpu_name[0] = '\0';  // 结束标记
}
```

**评述**：

- **`__get_free_pages`**：分配物理连续内存，这是 mmap 的前提——虚拟内存（`vmalloc`）无法直接映射
- **`pgprot_noncached`**：禁用 CPU 缓存，确保用户空间每次读取都是内核最新写入的值。代价是性能略低，但 CPU 统计数据量小（几 KB），影响可忽略
- **`remap_pfn_range`**：将内核物理页帧映射到用户空间虚拟地址，这是 mmap 零拷贝的核心
- **NO\_HZ 适配**：`get_cpu_idle_time_us()` 考虑了 tickless 内核的空闲时间统计，比直接读 `cpustat[CPUTIME_IDLE]` 更准确
- **结束标记**：`cpu_name[0] = '\0'` 告诉用户空间数据到此结束，避免遍历整个数组

### 5.18 功能点十八：离线检测与清理 — HostManager::ProcessLoop

**实现思路**：后台线程定期检查，超过 60 秒未收到数据的主机视为离线并移除。

**关键代码**：

```cpp
// manager/src/host_manager.cpp
void HostManager::ProcessLoop() {
    while (running_) {
        std::this_thread::sleep_for(std::chrono::seconds(60));

        auto now = std::chrono::system_clock::now();
        std::lock_guard<std::mutex> lock(mtx_);
        for (auto it = host_scores_.begin(); it != host_scores_.end();) {
            auto age = std::chrono::duration_cast<std::chrono::seconds>(
                now - it->second.timestamp).count();
            if (age > 60) {
                std::cout << "Removing stale host: " << it->first << std::endl;
                it = host_scores_.erase(it);
            } else {
                ++it;
            }
        }
    }
}
```

**评述**：

- **60 秒离线阈值**：Worker 默认 10 秒推送一次，6 次未推送视为离线
- **内存清理**：防止已下线服务器永远占用内存
- **不影响数据库**：历史数据保留在 MySQL 中，内存清理只影响实时查询
- **erase 安全**：使用 `it = host_scores_.erase(it)` 而非 `host_scores_.erase(it++)`，避免迭代器失效

### 5.19 功能点十九：Manager 启动与组件组装 — main.cpp

**实现思路**：在 main 函数中创建各组件，通过回调和依赖注入将它们组装起来。

**关键代码**：

```cpp
// manager/src/main.cpp
int main(int argc, char* argv[]) {
    // 1. 创建 gRPC 数据接收服务
    monitor::GrpcServerImpl service;

    // 2. 创建 HostManager 并设置回调
    monitor::HostManager mgr;
    service.SetDataReceivedCallback(
        [&mgr](const monitor::proto::MonitorInfo& info) {
            mgr.OnDataReceived(info);
        });

    // 3. 启动 HostManager 后台线程
    mgr.Start();

    // 4. 创建 QueryManager 并初始化 MySQL
    monitor::QueryManager query_mgr;
#ifdef ENABLE_MYSQL
    query_mgr.Init(kDefaultMysqlHost, kDefaultMysqlUser,
                   kDefaultMysqlPass, kDefaultMysqlDb);
#endif

    // 5. 创建查询服务
    monitor::QueryServiceImpl query_service(&query_mgr);

    // 6. 启动 gRPC 服务器，注册两个服务
    grpc::ServerBuilder builder;
    builder.AddListeningPort(listen_address, grpc::InsecureServerCredentials());
    builder.RegisterService(&service);        // 数据推送服务
    builder.RegisterService(&query_service);  // 查询服务

    auto server = builder.BuildAndStart();
    server->Wait();
}
```

**评述**：

- **两个 gRPC 服务共存**：`GrpcManager`（数据推送）和 `QueryService`（数据查询）注册在同一个 gRPC 服务器上，共享端口
- **依赖注入**：`QueryServiceImpl` 通过构造函数接收 `QueryManager*`，而非自己创建——便于测试和替换
- **条件编译**：`#ifdef ENABLE_MYSQL` 使 MySQL 成为可选依赖
- **组件组装顺序**：先创建底层依赖（HostManager、QueryManager），再创建上层服务（GrpcServerImpl、QueryServiceImpl）

### 6.1 与业界方案对比分析

#### 6.1.1 与 Prometheus 对比

| 维度           | 本项目                            | Prometheus                                       |
| -------------- | --------------------------------- | ------------------------------------------------ |
| **采集模式**   | Push（Worker 主动推送）           | Pull（Server 主动拉取）                          |
| **数据格式**   | Protobuf（二进制，紧凑）          | 文本格式 / OpenMetrics                           |
| **存储引擎**   | MySQL（关系型）                   | TSDB（自研时序数据库）                           |
| **查询语言**   | gRPC 接口（固定 9 个）            | PromQL（灵活查询语言）                           |
| **采集深度**   | 内核模块 + eBPF（可读内核级数据） | Node Exporter（仅 /proc/sysfs）                  |
| **评分系统**   | 内置多维度加权评分                | 无（需配合 Alertmanager 规则）                   |
| **异常检测**   | 内置阈值 + 变化率检测             | 需手动配置告警规则                               |
| **部署复杂度** | 低（单二进制 + 内核模块）         | 中（Server + Exporter + Alertmanager + Grafana） |
| **适用场景**   | 服务器调度选优、实时评分          | 通用监控、告警、可视化                           |

**核心差异**：

> Prometheus 是通用监控系统，Pull 模式适合标准化监控场景。本项目针对**服务器调度选优**这个特定场景，做了三个差异化设计：第一，Push 模式让 Worker 自主推送，Manager 零调度开销；第二，内核模块 + eBPF 实现了 /proc 无法获取的内核级数据精度；第三，内置评分算法直接输出服务器健康分数，调度系统无需二次计算。

#### 6.1.2 与 Zabbix 对比

| 维度         | 本项目                 | Zabbix                        |
| ------------ | ---------------------- | ----------------------------- |
| **架构**     | Worker-Manager（2 层） | Agent-Server-Proxy-DB（4 层） |
| **协议**     | gRPC（高效二进制）     | 自定义 TCP + JSON             |
| **采集方式** | 内核模块 + eBPF        | Agent 调用系统命令/脚本       |
| **配置方式** | 代码内置（零配置）     | Web UI 配置模板               |
| **扩展性**   | 新增 MonitorInter 子类 | 编写自定义脚本/模板           |

> Zabbix 是企业级通用监控，功能全面但架构重。本项目是轻量级专用系统：采集层用内核模块替代 Agent 脚本，精度和效率更高；传输层用 gRPC 替代自定义协议，跨语言兼容性更好；整体零配置部署，适合快速迭代的场景。

### 6.2 关键设计决策讲解

#### 6.2.1 为什么选择 Push 模式？

| 维度         | Push 模式（本项目）           | Pull 模式                        |
| ------------ | ----------------------------- | -------------------------------- |
| 数据流向     | Worker → Manager              | Manager → Worker                 |
| Manager 负载 | 低（被动接收）                | 高（主动轮询）                   |
| 实时性       | 高（数据变化即推送）          | 取决于轮询间隔                   |
| 扩展性       | Worker 数量增加不影响 Manager | Manager 需维护轮询列表           |
| 适用场景     | 大规模集群、实时性要求高      | 小规模、Manager 需要控制采集频率 |

**选择 Push 的理由**：

1. 降低 Manager 负载，Manager 只需被动接收数据
2. Worker 自主控制推送频率，适应不同采集需求
3. 天然支持动态扩缩容，新 Worker 直接推送即可
4. 适合大规模服务器集群场景

#### 6.2.2 为什么用 MySQL 而不是时序数据库？

> 三个原因：
>
> 1. **查询模式**：我们的查询不仅有时间序列范围查询，还有评分排序、异常检测等关系型查询，MySQL 的 SQL 支持更灵活
> 2. **部署简单**：MySQL 是最常见的基础设施，不需要额外引入新组件
> 3. **数据量可控**：当前规模（数百台服务器 × 10秒粒度）MySQL 完全能胜任
>
> 如果规模增长到万级服务器，可以考虑迁移到 TDengine：它专为时序数据设计，写入性能是 MySQL 的 10 倍+，且兼容 SQL 查询。

#### 6.2.3 为什么内核模块和 eBPF 混用？不全用 eBPF？

| 维度         | 内核模块                      | eBPF                                  |
| ------------ | ----------------------------- | ------------------------------------- |
| **功能**     | 无限制，可访问所有内核 API    | 受限，只能调用白名单函数              |
| **安全**     | 可能导致内核崩溃              | 验证器保证安全，不会崩溃              |
| **数据源**   | 可直接调用 kcpustat\_cpu() 等 | 只能通过 kprobes/tracepoints 间接获取 |
| **开发难度** | 高（需处理内核版本兼容）      | 中（BTF + CO-RE 解决兼容性）          |

> **原则：eBPF 能做的优先用 eBPF，做不到的才用内核模块。** CPU 统计和软中断数据需要调用 kcpustat\_cpu() 和 kstat\_softirqs\_cpu() 这些内核内部函数，eBPF 无法直接调用，所以用内核模块。网络统计只需要 skb 的数据包信息，eBPF TC Hook 完全够用，且更安全。

#### 6.2.4 评分算法的权重如何确定？

反向归一化 + 5 维加权：

- **CPU 35%**：高并发场景 CPU 是最关键资源
- **内存 30%**：内存不足直接导致 OOM
- **负载 15%**：反映系统整体压力，I/O 密集型场景系数取 1.5
- **磁盘 15%**：I/O 密集型场景磁盘是瓶颈
- **网络 5%**：内网环境带宽通常充足

> 权重基于场景分析确定，如果规模足够大，可用历史数据回归分析来优化权重。

### 6.3 Proto 接口设计要点

#### MonitorInfo 消息中的 singular vs repeated

```protobuf
message MonitorInfo {
  CpuLoad cpu_load = 5;          // singular — 全局只有一个负载值
  repeated CpuStat cpu_stat = 6; // repeated — 每个 CPU 核心一条
  MemInfo mem_info = 7;          // singular — 全局内存状态
  repeated NetInfo net_info = 8; // repeated — 每个网卡一条
  repeated DiskInfo disk_info = 9;// repeated — 每个磁盘一条
}
```

**设计原则**：CPU/网络/磁盘有多个实例，用 repeated；内存/负载全局唯一，用 singular。

## 七、面试常见问题

> 本章聚焦于功能的实现过程和架构理解。

### 7.1 架构设计类

#### Q1: 为什么选择 Push 模式而不是 Pull 模式？

1. **Manager 负载低**：Manager 被动接收，不需要维护轮询列表
2. **扩展性好**：新 Worker 上线只需向 Manager 推送，无需 Manager 侧配置
3. **实时性高**：数据产生即推送，不受轮询间隔限制
4. **适用场景**：大规模集群、实时监控、NAT 网络环境

#### Q2: 系统如何保证高可用？

1. **Worker 容错**：单 Worker 故障不影响其他 Worker 和 Manager
2. **Manager 容错**：可部署多 Manager 实例 + 负载均衡
3. **数据持久化**：MySQL 存储，Manager 重启后可恢复查询服务
4. **离线检测**：60 秒无数据自动清理内存缓存
5. **优雅降级**：eBPF 失败回退 procfs，内核模块未加载不影响其他采集

#### Q3: 如何扩展系统规模？

1. **Worker 扩展**：直接部署新 Worker，自动向 Manager 注册
2. **Manager 扩展**：多 Manager + MySQL 共享存储 + 负载均衡
3. **数据库扩展**：读写分离、分库分表（按 server\_name 哈希）
4. **查询扩展**：增加缓存层（Redis），减少数据库压力

***

### 7.2 功能实现类

#### Q4: 内核模块中 mmap 是怎么实现零拷贝的？

1. **原理**：将内核物理内存通过页表映射到用户空间虚拟地址
2. **实现步骤**：
   - 内核：\_\_get\_free\_pages 分配物理连续内存 → remap\_pfn\_range 建立映射
   - 用户：open 设备 → mmap 获取映射指针 → 直接通过指针读取
3. **为什么比 read 快**：read 需要系统调用 + 内存拷贝；mmap 建立映射后零系统调用、零数据拷贝
4. **关键细节**：pgprot\_noncached 禁用 CPU 缓存，确保每次读到最新值

#### Q5: eBPF 网络采集是怎么工作的？

1. **原理**：在内核中安全地运行沙箱程序，不修改内核源码
2. **TC Hook**：挂载在网卡 qdisc 层，每个数据包经过时更新 BPF Map 中的累计计数器
3. **用户空间读取**：遍历 BPF Map，通过前后差值计算速率
4. **为什么不用 XDP**：XDP 只有 ingress 方向，TC 同时支持 ingress + egress

#### Q6: 评分算法是怎么实现的？

1. **反向归一化**：使用率越低分数越高（1 - usage/100）
2. **五维加权求和**：CPU使用率×35% + 内存使用率×30% + 负载得分×15% + 磁盘利用率×15% + 网络得分×5%
3. **特殊处理**：负载得分用 1.5 系数（I/O 密集型场景容忍度更高），clamp 函数防止越界
4. **最终输出**：分数 × 100，范围 \[0, 100]

#### Q7: 变化率是怎么计算的？有什么用？

1. **公式**：(当前值 - 上次值) / 上次值，上次值为 0 时返回 0
2. **用途**：异常检测（>50% 触发告警）、趋势分析、容量规划

#### Q8: 数据是怎么从采集到入库的？

1. **采集层**：Worker 端 8 个监控器串行采集
2. **组装层**：MetricCollector::CollectAll() 填充 MonitorInfo 消息
3. **传输层**：MonitorPusher 独立线程每 10 秒 gRPC 推送到 Manager
4. **接收层**：GrpcServerImpl 接收数据，通过回调传给 HostManager
5. **处理层**：计算评分 + 变化率
6. **存储层**：一次性写入 MySQL 5 张表

***

### 7.3 设计模式与工程实践类

#### Q9: 项目中使用了哪些设计模式？

1. **策略模式**：MonitorInter 接口 + 各监控器实现，新增指标只需新增类
2. **组合模式**：MetricCollector 管理多个 MonitorInter，统一调用
3. **回调模式**：GrpcServerImpl 通过回调传递数据，解耦服务层和业务层

#### Q10: 线程安全如何保证？

1. **mutex + lock\_guard**：保护共享数据 host\_scores\_ 和 MySQL 连接
2. **atomic<bool>**：控制线程的安全退出
3. **锁粒度控制**：只在更新共享数据时加锁，回调在锁外执行，避免死锁

#### Q11: 数据库表为什么设计成 1 主表 + 4 详细表？

1. **减少主表宽度**：主表只存汇总数据，避免一张表几十个字段
2. **不同维度独立**：网络、磁盘、内存、软中断各有自己的详细表
3. **索引策略**：(server\_name, timestamp) 联合索引覆盖最常用查询
4. **变化率预计算**：写入时计算好并存储，避免查询时重复计算

## 八、总结

本项目是一个完整的分布式服务器性能监控系统，涵盖了从**内核级数据采集**到**应用层查询服务**的全栈实现。项目的核心价值在于：

1. **技术深度**：涉及内核模块开发、eBPF 编程、mmap 零拷贝等底层技术
2. **架构清晰**：Worker-Manager 分离、Push 模式、策略模式等设计
3. **功能完整**：采集 → 传输 → 存储 → 查询的完整链路
4. **实用价值**：可直接用于生产环境的服务器监控和调度

在面试中，应重点突出**内核模块和 eBPF 的技术深度**、**策略模式的架构设计**、**评分算法的业务理解**，以及**Push 模式的架构选型理由**。
